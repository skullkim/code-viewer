# 0001. 모듈 구조와 계약 경계

- 상태: 채택
- 날짜: 2026-08-29
- 결정자: backend-senior (프론트엔드 경계는 frontend-senior와 합의)

## 맥락
웹앱판은 HTTP가 경계면이었고, 계약 드리프트는 공유 TypeScript 타입 패키지(`@code-navigator/contract`)가
양쪽 컴파일 에러로 잡아줬다. 네이티브 앱에는 HTTP가 없다. 경계면을 무엇으로 삼고, 드리프트를
무엇이 잡아줄 것인가를 먼저 정해야 한다.

단일 타깃에 전부 넣으면 UI가 엔진 내부 타입에 직접 의존하게 되고, "계약"이 코드 리뷰에서만
지켜지는 관습이 된다. 웹앱판에서 기계 계약이 실제로 드리프트를 잡아낸 실적이 있으므로
같은 성질을 네이티브에서도 확보한다.

## 결정
SPM 타깃을 셋으로 나눈다.

| 타깃 | 소유자 | 의존 | 내용 |
|---|---|---|---|
| `CodeNavigatorContract` | backend-senior | **없음** | 값 타입 + 프로토콜. 경계면의 단일 소스 |
| `CodeNavigatorCore` | backend-senior | Contract, tree-sitter | 인덱싱·스캔·검색·감시·Neovim 세션 |
| `CodeNavigatorApp` | frontend-senior | Contract (+조립 지점에서만 Core) | SwiftUI 셸 |

- 계약은 **Swift 프로토콜과 값 타입**이다. `ProjectSession`, `EditorSession` 두 프로토콜이
  엔진의 전 표면이며, 앱은 이 프로토콜에만 의존한다.
- `Contract`는 의존성이 0이다. tree-sitter도 Foundation 특화 타입도 들어가지 않는다.
  덕분에 프론트엔드는 Core를 빌드하지 않고도 가짜 구현으로 테스트할 수 있다.
- 계약 변경은 **양쪽 타깃을 동시에 컴파일 실패**시킨다. 이것이 드리프트 방어선이다.
- 계약 문서의 단일 소스는 `_workspace/03_backend_architecture.md §3`, 코드의 단일 소스는
  이 타깃이다. 프론트엔드는 제안하고, 반영은 백엔드 시니어가 한다.

## 고려한 대안
1. **단일 타깃** — 가장 단순하고 빌드가 빠르다. 그러나 UI가 엔진 내부 타입을 자유롭게 쓰게 되어
   경계가 관습으로만 존재한다. 프론트엔드가 엔진 없이 테스트할 방법도 사라진다. 기각.
2. **Core만 분리(계약 타깃 없음, 앱→Core 직접 의존)** — 두 타깃이라 단순하다. 그러나 앱이 엔진
   구현 타입에 붙으므로 "가짜로 갈아끼우기"가 불가능하고, 무엇이 계약이고 무엇이 내부인지
   컴파일러가 구분해주지 않는다. 기각.
3. **별도 SPM 패키지로 계약 배포** — 버전 핀으로 드리프트를 늦출 수 있다. 1인 로컬 프로젝트에는
   과하고, 오히려 "버전이 달라서 안 깨지는" 상태를 만든다. 즉시 깨지는 편이 낫다. 기각.

## 트레이드오프
- 얻는 것: 컴파일 타임 드리프트 검출, 프론트엔드의 독립 테스트 가능성, 소유권의 물리적 경계.
- 잃는 것: 타깃 3개의 약간의 빌드 오버헤드, 계약 변경 시 파일을 하나 더 거쳐야 하는 번거로움.
- 되돌리기: 타깃 병합은 언제든 가능하다(파일 이동 + 매니페스트 수정). 되돌리기 비용이 낮은 결정.

## 결과
- 프론트엔드는 `EditorGridSnapshot` 같은 렌더 친화적 값 타입만 받는다. Neovim redraw 프로토콜의
  증분 갱신·스크롤 리전·하이라이트 테이블은 전부 엔진 안에 갇힌다.
- 앱은 프로젝트 파일을 쓰는 API를 아예 볼 수 없다. INV-3이 타입 수준에서 강제된다.
