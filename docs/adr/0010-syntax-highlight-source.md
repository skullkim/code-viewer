# 0010. 구문 강조의 출처 — Neovim이 분류하고, 앱이 색을 정한다

- 상태: 채택
- 영역: 백엔드 (backend-senior)
- 날짜: 2026-09-01

## 맥락

REQ-016은 "nvim을 따로 설정하지 않아도 코드가 색을 갖는다"를 요구한다. 강조 데이터가 어디서
오는지에 선택지가 둘 있었고, 둘의 비용 차이가 커서 착수 전 실측이 필요했다.

- **①** nvim의 강조 엔진(정규식 `syntax` 또는 treesitter)이 분류하고, 색이 그리드 셀로 온다.
- **②** 우리가 이미 번들한 tree-sitter 문법(Java·Kotlin·TypeScript)으로 직접 토큰을 계산해
  계약으로 넘긴다.

①이 싸 보이지만 AC-3(색은 디자인 토큰에서 온다)·AC-6(앱 테마가 사용자 colorscheme을 이긴다)과
충돌할 수 있다는 것이 착수 전의 우려였다. 그 충돌이 실재하는지가 결정을 갈랐다.

## 결정

**①을 택한다. 분류는 Neovim의 `syntax` 엔진이 하고, 색은 앱이 `nvim_set_hl`로 덮어쓴다.**

- 앱은 `EditorSyntaxPalette`(계약)를 세션에 내려주고, 세션은 그것을 Vim의 표준 강조 그룹
  (`Comment` `String` `Number` `Keyword`/`Statement` `Type` `Function` `Constant`)에 바른다.
  색의 소유자는 테마를 아는 앱이고, 세션은 바르기만 한다.
- **지원 언어 허용목록**(`java` `kotlin` `typescript` `typescriptreact` `javascript`
  `javascriptreact`)에 없는 파일타입은 버퍼 단위로
  `syntax = 'OFF'`를 걸어 평문으로 만든다(AC-4).
- 사용자 설정 파일은 읽지도 쓰지도 않는다. 매핑도 옵션도 이 세션에만 적용한다(INV-7).
- 같은 심볼 강조(AC-2)는 `CursorMoved`에서 `matchadd(<커서 아래 단어>)`로, 같은 세션 안에서 만든다.

## 실측 (spike, 2026-09-01 — Neovim 0.12.5, 트리 `c7a6bf7`)

| 잰 것 | 결과 |
|---|---|
| nvim 기본 강조 상태 | `g:syntax_on=1` — **정규식 syntax가 이미 켜져 있다** |
| 번들 treesitter 파서 | `c,lua,markdown,markdown_inline,query,vim,vimdoc` — **지원 3언어 없음**, `treesitter_active=false` |
| 지원 언어 구문 파일 | `java` `kotlin` `typescript` 각 1개 존재 (`javascript` `python`도) |
| 해석되는 표준 그룹 | Java `Comment,Constant,Type` · Kotlin `Comment,Constant,Type` · TypeScript `Comment,Constant,Function,Statement,Type` |
| 색이 계약까지 오는가 | **온다.** TS 파일에서 6종 색이 `EditorTextStyle.foreground`에 도착 |
| 뷰가 칠하는가 | 칠한다 — `GridFrameBuilder` + `GridRenderer.drawBackgrounds`가 전경·배경 모두 그린다 |
| **앱이 색을 덮으면 이기는가** | **이긴다.** `nvim_set_hl(0,'Comment',{fg=0xFF00FF})` 후 그리드의 주석 런이 `#9B9EA4` → `#FF00FF` |
| **미지원 언어를 평문화할 수 있는가** | **된다.** `vim.bo.syntax='OFF'` 후 파이썬 런의 전경색이 사라짐(기본값) |
| 같은 심볼 강조 | `matchadd` 로 붙인 배경이 그리드 런의 `style.background`로 도착 |

### 실측이 뒤집은 것 두 가지

1. **AC-1은 ①만으로는 성립하지 않는다.** nvim 기본 colorscheme에서 키워드(`const`·`class`·
   `export`)의 색이 `#E0E2EA`인데 **그것이 기본 전경색과 같다.** 색이 다른 것은 주석·문자열·
   함수명뿐이다. "IntelliJ처럼"이 아니라 사실상 흑백이며, 이것이 사용자가 강조를 요구한
   이유로 보인다. 그러므로 앱이 색을 덮는 것은 AC-3의 부수 효과가 아니라 **AC-1의 전제**다.
2. **AC-3·AC-6과 ①의 충돌은 실재하지 않았다.** `nvim_set_hl`이 colorscheme보다 나중에 적용되면
   이긴다. 우려는 가설이었고, 측정이 그것을 기각했다.

### 이 spike가 잡은 함정 1건 (측정 방법의 결함 — 재발 금지)

**1차 측정은 정반대의 결론을 냈다** — "앱이 덮어도 안 이긴다", "syntax=OFF해도 파이썬이 여전히
칠해진다". 둘 다 틀렸다. 원인은 `gridUpdates()`가 구독 즉시 마지막 프레임을 replay하는데
(`EventBroadcaster`), 프로브가 **행동 이전의 프레임**을 읽고 "안 변했다"고 판정한 것이다.
`revision`이 기준선을 넘은 프레임만 받도록 고치자 두 결론이 모두 뒤집혔다.

> **낡은 프레임은 정확히 "변하지 않음"처럼 보인다.** 그리드를 근거로 무언가를 판정하는 테스트는
> `revision` 기준선을 반드시 잡는다.

## 고려한 대안

1. **② 우리 tree-sitter 인덱스로 토큰을 계산해 계약으로 넘긴다.**
2. **①-treesitter — nvim에 treesitter 하이라이터를 켠다.**
3. **① + 앱 팔레트 (채택)**

## 트레이드오프

- **②**는 강조 권위가 둘이 된다. 더 무거운 문제는 **동기화**다 — 버퍼는 Neovim이 소유하고
  (INV-3) 우리 인덱스는 디스크에서 만들어진다. 사용자가 타이핑하는 동안 우리 토큰은 저장 전
  텍스트를 모르므로 **강조가 커서 뒤에서 어긋난다.** 그것을 고치려면 버퍼 텍스트를 계속 끌어와
  재파싱해야 하고, 그 순간 AC-5(강조가 편집을 느리게 하지 않는다)가 위험해진다. 계약 표면도
  새로 생긴다(토큰 배열·무효화 규약·좌표계). 우리가 번들한 문법은 **심볼 추출**을 위한 것이지
  강조를 위한 것이 아니며, 두 용도를 한 파서에 겹치면 인덱싱 성능 예산(REQ-NF)도 함께 흔들린다.
- **①-treesitter**는 색이 더 정확하다(`@keyword.function` 같은 세밀한 캡처). 그러나 실측대로
  **지원 3언어의 파서가 번들돼 있지 않다.** 파서를 앱 번들에 넣고 `runtimepath`에 꽂는 작업이
  선행돼야 하며, 그것은 이번 증분의 범위를 훨씬 넘는다. 얻는 것은 색의 세밀함뿐이고 AC는
  ①로 이미 전부 충족된다.
- **①**은 **계약 변경이 0이다.** 색이 이미 `hl_attr_define` → `EditorTextStyle` → `GridRenderer`로
  끝까지 흐르고 있다. 우리가 더할 것은 팔레트를 내려보내는 한 방향의 호출 하나다.

- **테스트 용이성**: 강조 여부를 그리드 스냅샷의 런 색으로 직접 단언할 수 있다. ②였다면
  토큰 배열과 화면 사이에 검증되지 않은 구간이 하나 더 생긴다.
- **단순성**: 우리가 짜는 코드는 "팔레트를 바른다"와 "허용목록 밖이면 끈다" 둘뿐이다.
- **변경 가능성**: 나중에 treesitter로 옮기고 싶으면 분류기만 바뀌고 팔레트 경로는 그대로다.
  변동점(색)과 고정점(분류)이 분리돼 있다.
- **되돌림**: 팔레트를 안 바르면 nvim 기본색으로 되돌아간다. INV-8("강조는 파생물")이 구조로
  지켜진다 — 팔레트 적용이 실패해도 파일은 열리고 편집된다.

## 채택 이유 (이 프로젝트 기준)

REQ-016의 여섯 AC 중 다섯이 ①로 **코드를 거의 더하지 않고** 충족되고, 남은 하나(AC-1)는
팔레트 적용이라는 한 방향 호출로 해결된다. ②는 코드·계약·성능 예산을 모두 늘리면서 같은 AC에
도달하고, 그 위에 **타이핑 중 강조가 어긋나는** 새 실패 모드를 얹는다.

무엇보다 AC-3·AC-6의 충돌 우려가 **측정으로 기각됐다.** 그 우려가 ②를 고를 유일한 이유였다.

## 결과 (구현 시 반드시 지킬 것)

- 팔레트는 **사용자 설정이 로드된 뒤**에 바른다. ADR-0006대로 설정은 `nvim_ui_attach` 시점에
  실행되므로, 적용 순서는 `attach → 설정 로드 → 팔레트`다. 순서가 뒤집히면 사용자 colorscheme이
  우리 색을 덮어 AC-6이 조용히 깨진다.
- 사용자 설정이 `ColorScheme` autocmd로 색을 다시 바를 수 있으므로, 같은 autocmd에 우리 적용을
  걸어 **뒤에 서게** 한다.
- 허용목록은 **파일타입 기준**이지 확장자 기준이 아니다. 판정 주체(nvim)가 쓰는 값으로 판정한다.
- `syntax = 'OFF'`는 **버퍼 단위**로 건다. 전역으로 끄면 허용 언어까지 죽는다.
- 강조 적용 실패는 편집을 막지 않는다(INV-8). 팔레트 호출은 실패해도 세션 기동을 되돌리지 않는다.
