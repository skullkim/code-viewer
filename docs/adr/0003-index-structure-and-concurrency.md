# 0003. 인덱스 자료구조와 동시성 모델

- 상태: 채택
- 날짜: 2026-08-29
- 결정자: backend-senior

## 맥락
인덱스는 정의 이동·참조·심볼 검색이 모두 올라타는 자료구조다. 성능 목표는 심볼 검색 ≤100ms,
증분 갱신 ≤500ms, 유휴 메모리 ≤150MB이며, INV-2(파생물 원칙)는 "인덱스는 소스에서 전량 재생성
가능하고 저장물이 없어도 재시작으로 복구된다"를 요구한다.

동시에 Swift 6 strict concurrency가 켜져 있다. 인덱스는 백그라운드 인덱싱 태스크가 쓰고
UI 태스크가 읽는 공유 가변 상태이므로, 동시성 모델을 명시적으로 정해야 컴파일이 통과한다.

## 결정
- **인메모리 정방향/역방향 맵, 디스크 영속 없음.**
  - 정방향 `[String: [SymbolDefinition]]` (파일 경로 → 그 파일의 정의들)
  - 역방향 `[String: [SymbolDefinition]]` (심볼 이름 → 정의 위치들), 정방향에서 파생
- **`actor SymbolIndex`로 감싼다.** 단일 writer 직렬화를 언어가 강제한다.
- 유일한 변경 연산은 `replaceFile(path:symbols:)`와 `removeFile(path:)` 둘뿐이다.
  생성·수정·이름변경이 전부 이 둘의 조합으로 표현된다.
- 인덱싱 병렬성은 **파싱 단계에만** 둔다: `TaskGroup`으로 파일을 병렬 파싱해
  `[SymbolDefinition]`를 만들고, actor에는 완성된 결과만 넣는다. 락 경합이 파싱을 막지 않는다.

## 고려한 대안
1. **SQLite/Core Data 영속 인덱스** — 재시작이 빨라지고 대형 레포에 유리하다. 그러나 (a) 스키마
   마이그레이션·손상 복구·스테일 검출이라는 새 문제군이 생기고, (b) INV-2가 "자명하게 성립"하던
   것이 "코드로 지켜야 하는 것"으로 바뀐다. 실측상 5,000파일 인덱싱이 목표(10초)의 한참 안쪽이라
   영속화가 사는 문제가 없다. 기각.
2. **`NSLock`/`DispatchQueue`로 보호하는 class** — actor보다 세밀한 제어가 가능하고 동기 읽기가 된다.
   그러나 Swift 6에서는 `@unchecked Sendable`로 컴파일러 검사를 꺼야 하고, 규율이 사람에게 돌아온다.
   락을 꺼야 할 실측 근거가 없다. 기각.
3. **읽기 전용 스냅샷 + Copy-on-Write** — 읽기가 actor hop 없이 동기로 끝나 가장 빠르다. 다만
   증분 갱신마다 맵 복제 비용이 생기고, 목표(검색 ≤100ms)는 actor로도 여유 있게 달성된다.
   측정 결과가 요구할 때 도입할 최적화이지 초기 설계가 아니다. 보류(필요 시 재검토).

## 트레이드오프
- 얻는 것: INV-2가 구조적으로 성립(저장물이 없으니 스테일 인덱스가 존재할 수 없다).
  동시성 안전을 컴파일러가 보증. 자료구조가 단순해 테스트가 쉽다.
- 잃는 것: 앱 시작 때마다 전량 인덱싱한다(실측 목표 대비 여유가 크지만 0은 아니다).
  아주 큰 레포(수만 파일)에서는 메모리가 선형으로 증가한다.
- 되돌리기: 영속 캐시는 나중에 **덧붙일 수 있는** 최적화다. 인메모리 구조가 진실의 원본으로
  남고 캐시는 워밍업 수단이 되므로, 되돌리기가 아니라 추가로 처리된다.

## 결과
- 삭제/이름변경 시 역방향 맵에서 빈 배열은 키째로 제거한다 — 유령 결과 금지(INV-1).
- `definitions(named:)`는 항상 경로·라인 순으로 정렬한 복사본을 돌려준다. 호출자가 스캔 순서에
  의존할 수 없게 만든다.
- 같은 이름의 정의가 여러 파일에 있으면 전부 보존한다. 중복 제거는 하지 않는다(REQ-005 AC-2).
