# 0007. 텍스트 오프셋 규약 = UTF-16 코드 유닛

- 상태: 채택
- 날짜: 2026-08-29
- 결정자: backend-senior

## 맥락
검색 결과 하이라이트(`MatchRange`), 미리보기 절단(200자), 시그니처 절단(120자)은 전부
"문자열 안의 위치"를 다룬다. 이 프로젝트에는 서로 다른 오프셋 공간이 최소 넷 있다.

| 공간 | 어디서 나오나 |
|---|---|
| UTF-8 바이트 | 파일 원본, 리터럴 검색의 바이트 탐색 |
| UTF-16 코드 유닛 | Swift `String.UTF16View`, `NSRange`, AppKit/SwiftUI 텍스트 API |
| 유니코드 스칼라 | Swift `String.unicodeScalars` |
| grapheme cluster | Swift `String`의 기본 `Character` |

한글·이모지가 섞이면 넷이 전부 다른 값을 낸다. 규약 없이 섞이면 **하이라이트가 한 글자씩 밀리는**
류의 버그가 나고, 테스트 픽스처가 ASCII뿐이면 끝까지 발견되지 않는다.

## 결정
**계약에 실리는 모든 텍스트 오프셋은 UTF-16 코드 유닛이다.** 반열린 구간 `[start, end)`.

- 근거 1: 렌더링 주체가 UTF-16을 쓴다. `NSRange`, `NSAttributedString`, `NSRegularExpression`이
  전부 UTF-16 기준이라, 프론트엔드가 변환 없이 바로 쓴다.
- 근거 2: 파서도 UTF-16을 준다. `swift-tree-sitter`의 `parse(_ string:)`은 소스를 UTF-16LE로
  인코딩해 넘기므로 `Node.range`가 **이미 UTF-16 코드 유닛 NSRange**다(실측 확인).
  별도 환산 없이 시그니처·이름을 잘라낼 수 있다.
- 근거 3: 웹앱판 계약이 UTF-16이었다(JS 문자열이 UTF-16). 이식 시 의미가 보존된다.

변환이 필요한 지점은 **리터럴 검색 한 곳뿐**이다: 바이트 탐색으로 찾은 UTF-8 오프셋을
UTF-16 오프셋으로 환산한다. 이 환산은 전용 함수 하나에 가두고 비ASCII 테스트로 고정한다.

## 고려한 대안
1. **UTF-8 바이트 오프셋** — 검색·파일 I/O와 자연스럽고 변환이 준다. 그러나 UI가 그릴 때마다
   역변환해야 하고, 변환 책임이 프론트엔드로 넘어간다. 경계면에 함정을 놓는 셈. 기각.
2. **Character(grapheme) 오프셋** — Swift에서 가장 "자연스러워" 보이지만, O(1) 인덱싱이 없고
   UI·파서·검색 어느 쪽과도 맞지 않아 변환이 세 배로 는다. 기각.

## 트레이드오프
- 얻는 것: 프론트엔드가 변환 없이 렌더. 파서 출력이 그대로 계약에 실림. 변환 지점이 하나로 국소화.
- 잃는 것: 서로게이트 페어(이모지 등)를 한가운데서 자를 수 있다. 미리보기 절단 시 이 경계를
  존중하도록 구현하고 테스트한다.

## 결과
- 모든 오프셋 테스트는 **한글이 섞인 픽스처**로 작성한다. ASCII 전용 테스트는 이 규약을 검증하지 못한다.
- `MatchRange`, `previewText`, `signature`의 문서 주석에 단위를 명시한다.
