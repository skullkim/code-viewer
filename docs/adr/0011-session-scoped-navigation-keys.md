# 0011. `gd`/`gr` — 세션 한정 매핑, 사용자 설정 우선, 빈 신호로 앱 호출

- 상태: 채택
- 영역: 백엔드 (backend-senior)
- 날짜: 2026-09-01

## 맥락

REQ-015는 Vim 모드에서 `gd`(정의로 이동)·`gr`(사용처 목록)을 **사용자가 nvim을 설정하지 않아도**
쓸 수 있기를 요구한다. 동시에 AC-6은 사용자의 `~/.config/nvim`에 이미 그 매핑이 있으면
**덮지 않을 것**을 요구하고, INV-7은 사용자 설정 파일을 수정하지 않을 것을 요구한다.

결정할 것이 셋이었다: 매핑을 어디에 심는가, 앱을 어떻게 부르는가, "사용자 매핑이 이미 있다"를
어떻게 판정하는가.

## 결정

**1. 매핑은 세션 안에만 심는다.** `nvim_exec_lua`로 `vim.keymap.set`을 호출한다. 사용자 설정
파일은 읽지도 쓰지도 않는다(INV-7). 앱이 띄운 프로세스가 죽으면 매핑도 함께 사라진다.

**2. 앱 호출은 `vim.rpcnotify`로 하고, 페이로드를 비운다.** 계약은
`AsyncStream<EditorNavigationRequest>`이고 값은 `.goToDefinition`·`.findReferences` 둘뿐이다.
심볼 이름을 싣지 않는다.

**3. 사용자 매핑 판정은 세 상태를 구별한다.** 설정 로드 후 `maparg(lhs,'n',false,true)`를 보고:

| 상태 | 판정 근거 | 우리 행동 |
|---|---|---|
| **없다** | `maparg`가 빈 사전 | 심는다 (`installed`) |
| **Neovim 자신의 기본** | `sid <= 0` 이고 스크립트 없음 | 대체한다 (`replacedEditorDefault`) |
| **사용자 것** | `sid > 0` 이고 스크립트가 **`$VIMRUNTIME` 밖** | **안 심는다** (`deferredToUserMapping`) |

판정 결과는 `EditorKeyMappingOutcome`으로 계약에 노출한다 — AC-6이 nvim 내부를 들여다보지
않고도 검증되게 하려는 것이다.

**4. `gr`의 접두 충돌은 Neovim 자신의 기본 매핑만 지워서 푼다.** `gra` `gri` `grn` `grr` `grt`
`grx` 중 **`sid <= 0`인 것만** 이 세션에서 삭제한다.

**5. 사용자가 `gr*`을 직접 정의했으면 `gr`을 아예 심지 않는다** (AC-7·AC-8).

여기서 두 요구가 정면으로 부딪힌다:

| 우리가 할 수 있는 것 | 깨지는 것 |
|---|---|
| 사용자의 `grr`을 지운다 | **AC-6** — 사용자 매핑은 사용자 것이다 |
| 두고 `gr`을 심는다 | **사용자의 `grr`이** 매번 `timeoutlen`을 기다린다 (실측 1,032ms) |
| 아무것도 안 심는다 | REQ-015 AC-2 가 이 사용자에게는 성립하지 않는다 |

**셋째를 택한다.** 앞의 둘은 우리가 사용자의 것을 망가뜨리는 쪽이고, 셋째만 사용자의 설정을
그대로 둔다. 키는 손버릇이고, 우리가 편의를 주려다 그 사람이 이미 쓰던 키를 느리게 만드는 것은
편의가 아니다.

**그러나 조용히 하지 않는다.** 판정을 `withheldToKeepUserPrefixKeys`로 남기고, 어느 키(`conflictingKeys`)
와 어느 파일(`userScriptPath`) 때문인지를 함께 싣는다. `deferredToUserMapping`과 **다른 case**인
이유는 사실이 다르기 때문이다 — 그쪽은 "사용자가 *이 키*를 갖고 있다"이고 이쪽은 "사용자가 *이
키로 시작하는 다른 키*를 갖고 있다"이다. 뭉개면 앱이 정확한 이유를 말할 수 없다.

**말하는 자리**: 계약의 `navigationKeyMappingOutcomes()`가 그 판정을 노출하고, **표시는 앱이
정한다**(설정 화면·상태바 툴팁 등 — 프론트엔드 결정). 엔진은 사실을 싣고 판단하지 않는다.
지난 빌드에서 여덟 번 만난 것이 *"조용히 아무 일도 안 일어남"*이었고, 이 분기가 정확히 그
모양이 될 수 있는 자리다.

## 실측 (spike, 2026-09-01 — Neovim 0.12.5, 트리 `c7a6bf7`)

| 잰 것 | 결과 |
|---|---|
| 세션 키맵 → `rpcnotify` → 앱 | **도달한다.** `gd` 누름부터 알림 수신까지 **21ms** |
| `gd`의 기존 매핑 | **없다.** `gd`는 매핑이 아니라 Vim 내장 명령(지역 선언으로 이동) |
| `gr`의 기존 매핑 | 없다 — **그러나 `gr`은 접두사다** |
| Neovim 0.12 기본 노멀 매핑 | `g%` `gO` `gc` `gcc` `gx` `gra` `gri` `grn` `grr` `grt` `grx` (`gr*`은 전부 `vim.lsp.buf.*`) |
| **`gr` 단독 발화까지** | **1032ms** — `timeoutlen`(1000ms) 을 통째로 기다린다 |
| `gr` 뒤에 다른 키가 올 때 | 23ms |
| 기본 `gr*` 6개 삭제 후 `gr` | **0ms** |
| 부착된 LSP 클라이언트 수 | **0** — 그 6개는 이 앱 안에서 아무 일도 하지 않는다 |
| 사용자 매핑 식별 | `sid=3`, `scriptname=<config>/nvim/init.lua`, `desc='user gd'` |
| 사용자 `grr` 픽스처 | 우리 `gr` 미설치 + 사용자 `grr` 생존 + `gd`는 영향 없음 (회귀 테스트로 고정) |
| Neovim 기본 매핑 식별 | `sid=-8`, 스크립트 없음 (`getscriptinfo`가 거부) |
| **설정 경로 접두 비교** | **심링크에 걸려 실패한다** — `stdpath('config')`는 `/var/…`, 스크립트 이름은 `/private/var/…` |

### 실측이 드러낸 결정적 사실

**요구사항이 근거로 삼은 관례가 요구사항과 어긋난다.** `01c_requirements.md`는 "LSP·최신 Neovim
관례"를 들어 `gr`을 사용처로 정했는데, **0.12의 실제 관례는 `grr`이고 `gr`은 그 접두사다.**
`gr`을 그대로 매핑하면 누를 때마다 1초가 멈춘다 — 사용자가 고른 "다른 Vim 환경과 손이
같아지는 쪽"의 정반대다.

이것은 코드를 읽어서는 알 수 없었다. 매핑을 심는 코드는 어느 쪽이든 똑같이 생겼고, 차이는
**누른 뒤에 흐르는 시간**에만 나타난다.

## 고려한 대안

### 매핑을 심는 곳
1. **사용자 `init.lua`에 우리 줄을 추가** — INV-7 정면 위반. 검토만 하고 기각.
2. **`--cmd`/`-c` 인자로 넘긴다** — 설정 로드 이전에 실행돼 사용자 매핑이 우리를 덮는다.
   AC-6과 방향이 반대다.
3. **설정 로드 후 `nvim_exec_lua` (채택)**

### 앱 호출 방식
1. **매핑이 심볼 이름을 실어 보낸다** — 앱은 검색만 하면 된다.
2. **매핑이 빈 신호만 보낸다 (채택)** — 앱이 `wordUnderCursor()`부터 다시 한다.

### `gr` 접두 충돌
1. **1초를 받아들인다.**
2. **`timeoutlen`을 줄인다.**
3. **`grr`로 요구를 바꾼다.**
4. **Neovim 자신의 `gr*`만 세션에서 삭제 (채택)**

## 트레이드오프

- **페이로드를 싣는 쪽**이 왕복 한 번을 아낀다. 그러나 앱에 ⌘B 경로와 `gd` 경로 **두 개의
  구현**이 생긴다. AC-3("⌘B는 그대로 동작한다")·AC-4("정의가 여럿이면 ⌘B와 같은 후보 목록")·
  AC-5("심볼이 아니면 이유를 말한다")가 전부 "두 경로가 같은가"에 걸리는데, 구현이 둘이면
  그 동일성은 **매번의 규율**이지 구조가 아니다. 빈 신호는 앱이 **이미 있는 핸들러를 그대로
  부르게** 만들어, 세 AC를 코드를 더하지 않고 충족시킨다. 21ms 중 왕복 하나를 아끼는 것은
  사람이 못 느끼는 이득이고, 지난 빌드가 비싸게 배운 것은 "같아야 하는 두 경로가 갈라지는 것"이었다.
- **`timeoutlen`을 줄이는 것**은 전역 옵션이라 사용자의 *다른* 모든 매핑의 대기 시간을 함께
  바꾼다. 한 키를 고치려고 사용자의 손버릇 전체를 건드리는 것이라 기각.
- **`grr`로 요구를 바꾸는 것**은 정당한 선택지다(그것이 실제 관례다). 그러나 사용자가 명시적으로
  `gr`을 골랐고, 이 결정은 되돌리기 쉽다 — 매핑 문자열 하나다. 리더에 판단을 올렸고, 승인이
  뒤집히면 `lhs` 상수만 바꾼다.
- **기본 `gr*` 삭제**의 위험은 "사용자가 LSP를 붙이는 설정을 갖고 있을 때 그 키를 잃는 것"이다.
  그래서 **`sid <= 0`인 것만** 지운다 — 사용자가 자기 `gr*`을 정의했다면 그것은 `sid > 0`이라
  살아남고, 그 경우 우리는 `gr` 매핑 자체를 포기한다. 즉 삭제 대상은 **정의상 Neovim이 기본으로
  준 것뿐**이며, 실측으로 그것들은 클라이언트가 0개라 동작하지 않는 상태다.

- **테스트 용이성**: 세 판정 상태가 계약의 enum이라 `XDG_CONFIG_HOME` 픽스처로 각각 단언된다.
  "사용자 매핑을 안 덮었다"가 nvim 내부 조회가 아니라 계약 값으로 검증된다.
- **위임 적합성**: 판정 로직(순수)과 적용 로직(RPC)이 갈려 판정 쪽은 격리 위임이 가능하다.
- **되돌림**: 매핑도 삭제도 세션 안에만 있다. 프로세스가 끝나면 흔적이 없고, 사용자 파일에는
  애초에 아무것도 쓰지 않았다.

## 채택 이유 (이 프로젝트 기준)

REQ-015의 여섯 AC 중 셋(AC-3·AC-4·AC-5)이 "⌘B와 같아야 한다"를 말한다. 그것을 규율이 아니라
**호출 그래프**로 만드는 설계가 빈 신호다. 나머지 셋 중 AC-6은 세 상태를 구별해야만 참이 되고,
그 구별은 실측으로 `sid`와 스크립트 경로에서 가능함을 확인했다.

`gr`의 1초는 측정하지 않았다면 라이브에서야 드러났을 것이고, 그때는 "느리다"는 인상만 남고
원인은 접두 충돌이라는 보이지 않는 곳에 있었을 것이다.

## 결과 (구현 시 반드시 지킬 것)

- 매핑 설치는 **설정 로드 이후**다. ADR-0006대로 `nvim_ui_attach` 전에는 사용자 `init.lua`가
  실행되지 않으므로, `attach` 이전에 판정하면 **사용자 매핑을 항상 "없음"으로 읽는다.**
  AC-6이 조용히 무력화되는 정확한 경로다.
- `sid`는 **음수일 수 있고 `getscriptinfo`가 그것을 거부한다**(실측: `E475: Invalid value for
  argument sid: -8`). 조회 전에 `sid > 0`을 확인한다.
- "사용자 것"의 판정은 `sid > 0`만으로 부족하다 — 런타임 vimscript도 양수 `sid`를 가질 수 있다.
  판정 기준은 **"설정 디렉토리 안인가"가 아니라 "`$VIMRUNTIME` 밖인가"**다.
- ⚠ **경로 비교 전에 심링크를 푼다**(`vim.uv.fs_realpath`). 실측에서 `stdpath('config')`는
  `/var/…`를 주고 `getscriptinfo`의 스크립트 이름은 `/private/var/…`를 줘서 **접두 비교가
  실패했다.** macOS의 `/var`는 `/private/var`의 심링크다. 이 실패의 방향이 나쁘다 — 사용자의
  매핑을 "우리 것이 아님"으로 읽지 못해 **덮어쓰게 된다.** AC-6이 금지하는 바로 그 결과다.
  그리고 `~/.config/nvim`을 dotfiles 저장소로 심링크하는 것은 흔한 설정이라, 이것은 테스트
  환경만의 인공물이 아니라 실사용에서 나는 실패다.
- 삭제는 `pcall`로 감싼다. 없는 매핑을 지우면 오류가 나고, 그 오류가 세션 기동을 죽여선 안 된다.
- 세 상태를 **하나의 불리언으로 뭉개지 않는다.** "매핑이 있다"는 질문의 답은 셋이다.
