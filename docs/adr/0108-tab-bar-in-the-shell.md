# ADR-0108: 탭 바를 고정 높이 행으로 넣는다 — 셸 레이아웃 확장

- 상태: 채택
- 영역: 프론트엔드 (frontend-senior)
- 날짜: 2026-08-30
- 확장: [ADR-0104](0104-shell-layout.md) 의 규칙을 행 하나 늘려 그대로 적용한다

## 맥락

`02b_design.md` D-A 가 탭 바의 **위치**를 정했다(툴바 바로 아래, 창 전폭 32px). 그건 디자인
결정이고, 이 ADR 이 정하는 것은 **그것을 무엇이 보장하느냐**다.

ADR-0104 는 이 빌드에서 실제로 난 결함 하나 때문에 존재한다: 에디터가 고유 크기를 주장해서
**상태바를 화면 밖으로 밀어냈다.** 0104 는 "고정 높이 크롬을 먼저 배치하고 3영역이 잔여를
갖는다"로 그것을 막았다.

지금 그 행이 하나 는다. `02b §11-1` 이 같은 함정을 다시 밟기 쉽다고 경고한 자리다 — 행이 늘면
잔여 계산이 바뀌고, 창이 작을 때 무엇이 먼저 밀려나는지가 다시 정의되지 않은 상태가 된다.

## 결정

**탭 바는 고정 높이 크롬이다. 0104 의 순서를 그대로 따른다.**

```
VStack(spacing: 0) {
    툴바      .frame(height: 48)   고정
    탭 바     .frame(height: 32)   고정 — 이번에 추가
    콘텐츠    .frame(maxHeight: .infinity)   잔여
    상태바    .frame(height: 26)   고정
}
```

- **잔여 높이는 콘텐츠 하나만 갖는다.** 고정 크롬 합계는 106px 이다(48+32+26).
- **`ShellLayout.resolve` 가 이 계산의 단일 소스다.** 0104 가 "치수 계산은 뷰가 아니라 순수
  함수가 한다"고 정했고, 행이 늘어난 지금 그 규칙이 더 중요해진다. 크롬 높이를 뷰에 흩어
  적으면 셋 중 하나만 고쳐지는 날이 온다.
- **탭이 1개여도 탭 바는 표시한다** — 리더 판정(`02b §12-1`). 따라서 크롬 높이는 탭 수와
  무관한 상수이고, 레이아웃에 조건 분기가 없다.
- **탭 바는 잔여를 요구하지 않는다.** 탭이 많아지면 폭이 모자라지 넓어지지 않는다. 넘침은
  높이가 아니라 폭 문제이고, 넘침 메뉴(`02b §8`)가 폭 안에서 해결한다.

## 고려한 대안

**A. 탭 바를 툴바 안에 넣는다** (타이틀바 겸용)
행이 안 늘어나니 0104 를 안 건드린다. 그러나 `02b` D-A 가 수치로 기각했다 — 900px 창에서 탭에
남는 폭이 200px 미만이고, 창 제목(= 활성 파일 이름 + 더티 표시)을 탭에 내주면 그 정보가
사라진다. **레이아웃을 안 건드리려고 정보를 버리는 거래**다.

**B. 탭 바에 잔여 높이를 조금 준다** (내용에 따라 늘어나는 스트립)
탭 라벨이 길거나 두 줄이 되면 자연스럽게 커진다. 그러나 그것이 정확히 **에디터가 상태바를
밀어냈던 메커니즘**이다. 콘텐츠가 크기를 정하게 두면 무엇이 먼저 밀려나는지가 정의되지 않는다.
라벨 길이는 높이가 아니라 말줄임(`.truncationMode(.middle)`)으로 해결한다.

**C. 고정 높이 크롬 행으로 추가한다 (채택)**

## 트레이드오프

- **테스트 용이성**: C 는 "창 높이 480 에서 상태바가 보이는가"를 `ShellLayout.resolve` 의 값
  비교로 검증한다 — 렌더링 없이. B 는 실제 레이아웃을 돌려봐야 알 수 있고, 그건 이 빌드에서
  이미 놓친 종류의 검증이다.
- **단순성**: C 는 조건 분기가 없다(탭 수와 무관한 상수). B 는 "언제 늘어나는가"라는 규칙이
  하나 더 생긴다.
- **변경 가능성**: 크롬 높이가 한 곳에 모여 있으면 행을 또 늘릴 때(렌더 헤더 바가 후보다)
  같은 자리만 고친다. 다만 렌더 헤더는 **에디터 영역 위 오버레이**이므로 크롬 행이 아니다
  (`02b` D-B — 그리드를 리사이즈하면 nvim 전면 리드로가 난다).
- **되돌림**: 값 하나와 행 하나라 비용이 낮다.

## 채택 이유

**이미 한 번 난 결함을 같은 방법으로 막는다.** 0104 는 사후에 배운 규칙이고, 지금은 그 규칙을
적용할 자리가 하나 더 생겼을 뿐이다. 새 결정을 내리는 게 아니라 **있는 결정을 지키는 것**이
맞는 상황이다.

`02b §11-1` 이 프론트에게 정확히 이 함정을 경고했다는 사실 자체가, 이 규칙이 문서가 아니라
코드(순수 함수 + 테스트)에 있어야 하는 근거다.

## 결과 (구현 시 지킬 것)

- 최소 창(720×480)에서 **상태바가 보이는지**를 테스트로 고정한다. 크롬 106px 을 뺀 잔여가
  3영역 최소 높이를 만족하는지 확인하고, 못 하면 그때 무엇을 접을지는 `02b §5.3` 표를 따른다.
- 탭 바 높이 상수는 `ShellLayout.Metrics` 에 둔다 — 툴바·상태바 높이가 이미 거기 있고, 크롬
  예산은 셋이 함께 있어야 합계(`fixedChromeHeight`)가 한 곳에서 계산된다. 뷰가 32 를 직접
  적지 않는다.
- **이 결정이 지켜지는지 확인하는 곳**: `ShellLayoutTabBarTests` — 크롬 합계 106, 최소 창
  480 에서 콘텐츠 374, 음수 방지. 크롬 예산에서 탭 바를 빼면 3건이 Red 가 되는 것을 실측했다.
