# 0005. 파일 감시 전략 — FSEvents + 디바운스 + 대량 변경 폴백

- 상태: 채택
- 날짜: 2026-08-29
- 결정자: backend-senior

## 맥락
REQ-009는 저장·수정·삭제·추가·이름변경이 인덱스에 반영되고(INV-1 스테일 0), 대량 변경
(git checkout 등)에서 "이벤트 폭주로 죽지 않고 전체 재스캔으로 폴백"할 것을 요구한다.
웹앱판은 chokidar + 디바운스 300ms + 50파일 임계로 해결했다. 네이티브에서는 감시 API 자체를
고르고, 그 API가 실제로 어떤 이벤트를 주는지 실측해야 했다.

## 결정
**FSEvents**(`FSEventStreamCreate`, `kFSEventStreamCreateFlagFileEvents | NoDefer | UseCFTypes |
WatchRoot`)로 프로젝트 루트를 재귀 감시하고, 웹앱판의 디바운스·임계 구조를 그대로 가져온다.

- 디바운스 **300ms**(웹앱판과 동일), 마지막 이벤트 기준으로 타이머 재시작.
- 대기 중 경로 수가 **50개 이상**이면 증분 갱신을 버리고 전체 재스캔으로 폴백.
- FSEvents가 `MustScanSubDirs`(+`UserDropped`)를 보내면 **즉시 전체 재스캔 예약**.
  단 폭주 중에 재스캔이 시작되지 않도록 마지막 이벤트로부터 1초 더 기다린 뒤 실행한다.
- 이벤트 → 동작 판정 규칙: **`ItemIsFile`이 서 있고 `ItemRemoved`가 없으면 "다시 읽어라"**.
  개별 플래그 비트를 신뢰하지 않는다.
- 지원 언어가 아닌 파일의 이벤트는 대기 목록에 넣지 않는다(`.md` 저장이 재인덱싱을 유발하지 않게).
- 앱 내부 저장은 감시에만 의존하지 않는다. Neovim의 `BufWritePost`가 저장된 경로를 직접
  알려주므로(ADR-0006) 그 경로는 즉시 갱신 대상이 된다. 파일 감시는 **외부 변경**의 안전망이다.

## 실측 (spike, 2026-08-29)
| 관측 | 값 |
|---|---|
| 단일 변경 감지 지연 (latency 0.1s + NoDefer) | 최소 11.5ms / 중앙 12.6ms / 최대 18.3ms |
| 콜백당 최대 이벤트 수 | **32개** — 300~20,000파일 모든 규모에서 예외 없이 동일 |
| git checkout 300파일 | 1,505 이벤트 / 53 콜백 / ~213ms 내 도착, `MustScanSubDirs` 미발생 |
| 8,000파일을 400디렉토리에 분산 생성·삭제 | 16,702 이벤트 / 574 콜백, `MustScanSubDirs` 미발생 |
| 20,000파일을 **한 디렉토리에** 생성·삭제 | 36,535 이벤트 / 1,246 콜백, `MustScanSubDirs+UserDropped` **4회 발생** |
| 이름변경 | 콜백 1회에 옛 경로·새 경로 **둘 다** 도착(같은 배치, id는 옛 경로가 작음) |
| 에디터식 원자적 저장(임시파일 → rename) | 대상 경로가 한 배치에 **두 번** 등장, 플래그는 `ItemRenamed`와 `ItemModified`가 OR |
| Neovim의 실제 `:w` (기본 `backupcopy=auto`) | **제자리 쓰기** — inode 불변, 즉 평범한 수정 이벤트 |

`MustScanSubDirs`는 총 이벤트 수가 아니라 **디렉토리당 이벤트 집중도**에 반응했다.
그리고 그것은 개별 파일이 아니라 **감시 루트 경로에** 단독(batch=1)으로 도착한다.

## 고려한 대안
1. **`DispatchSource.makeFileSystemObjectSource`(kqueue)** — 파일 디스크립터 단위 감시.
   재귀 감시가 없어 디렉토리를 직접 훑어 등록해야 하고, 수천 파일이면 fd를 수천 개 연다.
   대형 레포에서 fd 한계에 부딪힌다. 기각.
2. **주기적 폴링(mtime 스캔)** — 가장 단순하고 이식성이 좋다. 그러나 5,000파일 stat을 반복하는
   유휴 비용이 생기고(NF-002 자원 목표에 역행), 저장 후 반영 지연이 폴링 주기에 묶인다. 기각.
3. **FSEvents (채택)** — OS가 커널 수준에서 코얼레싱까지 해준다. 특별한 entitlement가 필요 없음을
   실측 확인. 대량 변경에서 드롭 신호까지 표준으로 제공한다.

## 트레이드오프
- 얻는 것: 자원 비용이 사실상 0인 재귀 감시, OS가 제공하는 폭주 방어(드롭 신호), 새로 생긴
  하위 디렉토리 자동 감시(실측 확인 — 재등록 불필요).
- 잃는 것: macOS 전용(이 앱은 macOS 전용이므로 비용 아님). 플래그 의미가 지저분해
  "무엇이 일어났는가"를 정확히 복원할 수 없다 — 그래서 위의 단순한 판정 규칙을 쓴다.
- 되돌리기: 감시자는 프로토콜 뒤에 있어 폴링 구현으로 교체 가능하다.

## 결과 (구현 시 반드시 지킬 것)
- **콜백 코드는 `main.swift`에 두지 않는다.** Swift 6에서 `main.swift`의 최상위 선언은 암묵적으로
  `@MainActor`가 되어 `@convention(c)` 콜백으로 넘길 수 없다(실측: 컴파일 에러). 별도 파일에 둔다.
- 컨텍스트는 캡처가 아니라 `Unmanaged<...>.passUnretained().toOpaque()`로 전달한다.
- **감시 루트는 `realpath(3)`로 정규화한다.** FSEvents가 돌려주는 경로는 심링크가 완전히 해소된
  형태(`/tmp` → `/private/tmp`)인데, Foundation의 `URL.resolvingSymlinksInPath()`는 `/tmp`·`/var`를
  일부러 해소하지 않아 **경로 비교가 조용히 전부 빗나간다**(실측 확인).
- `WatchRoot` 플래그를 켠다. 켜지 않으면 감시 루트가 이동·삭제될 때 스트림이 **조용히 죽는다**.
- 한 배치에 같은 경로가 중복 등장할 수 있다. 경로를 키로 하는 맵에 모아 자연스럽게 합친다.
