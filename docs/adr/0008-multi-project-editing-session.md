# 0008. 여러 프로젝트를 동시에 열 때의 편집 세션 모델

- 상태: **채택** (리더 승인 2026-08-30, frontend-senior 합의 대기)
- 날짜: 2026-08-30
- 결정자: backend-senior · 합의: frontend-senior

## 맥락
REQ-012는 프로젝트를 여러 개 동시에 열고 탭으로 전환할 것을 요구하며, 사용자가 **열린 프로젝트의
인덱스를 전부 메모리에 유지**(즉시 전환)하기로 결정했다. INV-5는 탭 간 격리를 요구한다.

편집 세션을 어떻게 늘릴지가 갈림길이다. 이 앱의 존재 이유가 "IntelliJ 대비 메모리 1/10"이므로
(REQ-NF-002), 선택은 수치로 정해야 한다.

## 실측 (2026-08-30, 실제 Neovim 0.12.5, `ps -o rss`)

| 모델 | 1개 | 2개 | 3개 | 4개 |
|---|---|---|---|---|
| **A. 프로젝트당 프로세스** | 15.1MB | 30.2MB | 45.2MB | **60.1MB** |
| **B. 프로세스 하나 + 탭페이지** | 13.5MB | 15.0MB | 15.2MB | **15.5MB** |

- 모델 A는 프로젝트당 **약 15MB**가 그대로 늘어난다.
- 모델 B는 추가 탭당 **약 0.7MB**다. 4개 기준 **약 4배 차이**(45MB)다.
- 격리 확인: `tcd`로 **탭페이지마다 작업 디렉토리가 독립**임을 실측했다(탭1 `/usr`, 탭2 `/private/tmp`).

인덱스 쪽 비용은 별도다 — 기존 실측으로 25,000심볼당 약 19MB. 따라서 **프로젝트 하나를 더 여는
총비용은 모델 B에서 약 20MB**(인덱스 19 + 편집기 0.7)이고, 모델 A에서는 약 34MB다.

## 결정
**모델 B — Neovim 프로세스 하나가 프로젝트당 탭페이지 하나를 갖고, `tcd`로 작업 디렉토리를 분리한다.**

- 앱의 탭 ↔ Neovim 탭페이지가 1:1로 대응한다.
- 프로젝트를 열면 `tabnew` + `tcd <루트>`, 탭을 닫으면 `tabclose`.
- UI는 여전히 하나의 그리드에 붙는다. Neovim이 현재 탭페이지를 그리므로 전환이 곧 그리드 전환이다.
- 인덱스는 프로젝트마다 별개 `ProjectIndexer`를 유지한다(그쪽은 모델과 무관하게 프로젝트당 하나다).

## 고려한 대안과 트레이드오프
**모델 A(프로젝트당 프로세스)가 나은 점이 둘 있다. 그것을 알고 B를 고른다.**

1. **크래시 격리** — A는 한 프로젝트의 Neovim이 죽어도 나머지가 산다. B는 전 탭이 함께 죽는다.
   완화: REQ-004 AC-5가 이미 사망 감지와 재기동을 요구하고 그 경로는 구현·테스트돼 있다.
   재기동 시 모든 탭을 복원해야 하므로, 그 복원은 REQ-012 AC-4(재시작 시 탭 복원)와 **같은 코드**다.
   즉 B는 이미 필요한 기능을 재사용하고, A는 격리를 위해 45MB를 지불한다.
2. **프로젝트별 로컬 설정**(`exrc`/`.nvim.lua`) — Neovim은 기동 시점의 작업 디렉토리에서 로컬 설정을
   읽는다. B에서는 첫 프로젝트의 것만 적용된다. **이것이 B의 실질적 손실이다.**
   완화 근거: `exrc`는 Neovim 기본값이 **꺼짐**이고, REQ-004 AC-3이 요구하는 것은 사용자의
   `~/.config/nvim` 설정이며 그것은 B에서도 온전히 적용된다. 프로젝트 로컬 설정이 필요하다는
   요구가 실제로 나오면 그때 A로 전환하거나 탭별 프로세스를 혼합한다.

**되돌리기 비용**: 편집 세션은 `EditorSession` 프로토콜 뒤에 있다. 모델 교체는 그 구현 하나를
바꾸는 일이고 계약은 그대로다. A로 되돌리는 것이 비싸지 않다는 점이 B를 먼저 시도할 근거이기도 하다.

## 추가 실측 — 탭을 닫으면 메모리가 회수되는가 (REQ-012 AC-3)

각 프로젝트에 30파일 × 200줄을 실제로 열어 재봤다.

| 단계 | RSS |
|---|---|
| 기준선(빈 버퍼) | 13.6MB |
| 탭 4개까지 열기 | 20.3 → 25.4 → 30.5 → **35.3MB** |
| 탭 3개 닫기 + 버퍼 삭제 | **35.3MB** (회수 0.0MB) |
| 같은 3개를 **다시 열기** | **35.5MB** (1회차 피크 대비 **+0.4MB**) |

**닫아도 RSS는 줄지 않지만 누수가 아니다.** 다시 열었을 때 거의 늘지 않는다는 것이 판정 근거다 —
해제된 메모리가 프로세스 안에서 재사용되고 있으며, OS로 반환되지 않을 뿐이다. 할당자의 정상 동작이다.

**이것이 뜻하는 바:**
- 실질적 상한은 "지금까지 연 프로젝트 총수"가 아니라 **"동시에 열었던 최대 개수"**다.
  세션 내내 프로젝트를 여닫아도 무한히 늘지 않는다.
- **인증 시 주의**: AC-3의 "메모리 잔존 없음"을 **RSS 감소로 판정하면 안 된다.** 정상 동작을
  결함으로 오독하게 된다. AC-3은 (a) 고아 프로세스가 없는지, (b) 엔진 쪽 인덱스가 해제되는지,
  (c) 여닫기를 반복해도 증가하지 않는지로 판정한다. (c)가 진짜 회귀 신호다.

## 결과 (구현 시 지킬 것)
- **탭을 닫으면 그 탭페이지와 인덱서가 함께 정리된다**(REQ-012 AC-3). 프로세스가 하나이므로
  고아 프로세스 문제는 탭 단위로는 사라지지만, **앱 종료 시 `shutDown()` 배선은 여전히 필요하다**(D-2).
- **INV-5(탭 간 격리)는 `tcd`가 보장한다 — 실측했다.** 다만 레지스터·마크·점프목록처럼
  **Neovim이 전역으로 두는 상태는 탭 간에 공유된다.** 이것이 격리의 한계이며, 복사/붙여넣기가
  탭을 넘나드는 것은 오히려 사용자가 기대하는 동작이라 문제로 보지 않는다.
- **복사 후 선택 해제**: 표준 모드에서 `copySelection` 뒤 삽입 상태로 복귀하므로 선택이 풀린다.
  맥 관례는 복사 후 선택 유지지만, 표준 모드에서는 **타이핑 연속성이 더 큰 기대**라고 보아 그렇게 뒀다.
  사용자가 다르게 느끼면 `runModeIndependently(resumingTypingInStandardMode:)`를 `copySelection`에서만
  `false`로 주면 된다 — 한 줄이다.
- **메모리 보고**: REQ-NF-002를 "프로젝트 1개 기준"으로 읽되, 탭당 증가분(약 20MB)을 기록한다.
  프로젝트 4개 기준 총계는 약 95MB(앱 기준선) + 3×20MB ≈ **155MB**로, IntelliJ 1~2GB 대비
  여전히 1/10 이하다. 이 수치는 조립 후 실측으로 갱신한다.
