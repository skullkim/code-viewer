# ADR-0107: 탭이 상태의 단위가 된다 — `ProjectWorkspace` 를 탭 안으로 좁힌다

- 상태: 채택
- 영역: 프론트엔드 (frontend-senior)
- 날짜: 2026-08-30
- 대체: [ADR-0106](0106-project-workspace.md) 을 **폐기하지 않고 범위를 좁힌다** (아래 "0106 과의 관계")

## 맥락

REQ-012 는 프로젝트를 여러 개 동시에 열고 탭으로 전환할 것을 요구하고, INV-5 는 탭 간 격리를
요구한다. 지금 앱의 상태는 `AppModel` 하나에 모여 있고 그것은 **프로젝트가 하나뿐**이라는 전제
위에 서 있다.

`01b_requirements.md` 는 이 충돌을 시니어 판정 항목으로 명시했다: `ProjectWorkspace` 의 불변식
("인덱스와 편집기가 한 프로젝트를 함께 따라간다")은 탭이 여럿이면 전제가 바뀐다.

무엇이 탭별이고 무엇이 창/앱 전역인지는 `02b_design.md §1.1` 이 화면 계약으로 이미 확정했다.
이 ADR 은 그 표를 **타입으로 옮기는 방법**을 정한다.

## 결정

**탭 하나가 상태의 단위다.** `ProjectTab` 이 한 프로젝트의 트리·에디터·검색·인덱스 상태를
소유하고, `AppModel` 은 **탭 목록과 활성 탭**, 그리고 창/앱 전역 상태만 소유한다.

```
AppModel                      창·앱 전역
├─ tabs: [ProjectTab]         순서 = 화면 순서 (REQ-012 AC-1)
├─ activeTabID                전환은 이 값 하나를 바꾸는 일이다 (AC-2 "즉시")
├─ inputMode                  앱 전역 (REQ-010 AC-6)
├─ theme                      앱 전역 (REQ-011 AC-4)
└─ 창 크기·분할 비율·표시 여부  창 전역 (REQ-011 AC-3)

ProjectTab                    탭 소유 (INV-5)
├─ projectRoot / 표시 이름
├─ 트리(펼침·스크롤·선택)
├─ 열린 파일·커서·더티
├─ 참조 패널 / 전문 검색
├─ 인덱스와 그 상태            메모리 상주 (AC-2)
└─ 파일별 렌더/소스 선택        (REQ-013, ADR 별건)
```

**`ProjectWorkspace` 의 불변식은 유지하되 탭 안에서 성립한다.** "인덱스와 편집기는 함께
움직인다"는 이제 "**한 탭의** 인덱스와 편집기는 함께 움직인다"로 읽는다. 0106 이 막으려던
버그(인덱스만 옮기고 편집기는 이전 루트에 남는 것)는 탭이 여럿이어도 그대로 존재하고, 오히려
탭마다 어긋날 수 있으므로 **더 필요해진다.**

**전환은 상태 스왑이지 재생성이 아니다.** AC-2 의 "재인덱싱 대기 없이 즉시"는 탭별 상태를 모두
메모리에 두고 `activeTabID` 만 바꿔서 얻는다. 뷰를 다시 만들면 "즉시"가 깨진다(`02b §11-5`).

## 고려한 대안

**A. `AppModel` 을 탭 수만큼 복제하고 창 전역 상태도 함께 복제한다**
가장 손이 덜 간다 — 기존 타입을 그대로 배열에 담으면 된다. 그러나 창 크기·분할 비율·테마·입력
모드가 탭마다 복제되어 **어느 사본이 진짜인지 정의되지 않는다.** 탭을 전환할 때 분할 비율이
같이 바뀌면 사용자는 창이 제멋대로 움직인다고 느낀다. `02b §1.1` 이 이 넷을 명시적으로
창/앱 전역으로 못박은 이유다.

**B. 탭별 상태를 딕셔너리 여러 개로 흩는다** (`treeStateByTab`, `searchStateByTab`, …)
기존 `AppModel` 을 거의 안 건드린다. 대신 **탭 하나를 닫을 때 지워야 할 곳이 N군데**가 되고,
하나를 빠뜨리면 닫은 프로젝트의 검색 결과가 다음 탭에 나타난다. REQ-012 AC-3 의 "정리"가
사람의 규율에 의존하게 된다. 이 빌드에서 규율에 기댄 것은 대체로 한 번씩 깨졌다.

**C. 탭별 상태를 한 타입에 모은다 (채택)**

## 트레이드오프

- **테스트 용이성**: C 는 "탭 A 를 조작해도 탭 B 가 안 변한다"(INV-5)를 **값 비교 한 번**으로
  검증한다. B 는 딕셔너리마다 따로 확인해야 하고, 그건 불변식이 아니라 구현을 테스트하는 것이다.
- **단순성**: A 가 타입이 가장 적다. 그러나 그 단순함은 "어느 사본이 진짜인가"라는 답 없는 질문을
  코드에 남긴다. 타입 수보다 **정의되지 않은 상태가 비싸다.**
- **변경 가능성**: 탭이 소유할 것이 늘어나면(REQ-013 의 렌더/소스 선택이 당장 그렇다) C 는 한
  곳만 는다. B 는 딕셔너리가 하나 더 는다.
- **위임**: `ProjectTab` 경계가 서면 탭 바 뷰·탭 판단 로직·복원 로직이 서로 안 겹치게 쪼개진다.
- **되돌림**: 탭별/전역 경계는 `02b §1.1` 이 화면 계약으로 이미 정한 것이라, 되돌린다면 그건
  구현이 아니라 설계를 되돌리는 일이다. 되돌릴 결정이 아니라 **따를 결정**에 가깝다.

## 채택 이유

**INV-5 를 주석이 아니라 소유 관계로 만든다.** "다른 탭의 상태를 바꾸지 않는다"는 규칙을 지키는
방법이, 애초에 **다른 탭의 상태에 손이 닿지 않는 구조**를 만드는 것이다. 0106 이 "두 절반을
따로 부를 방법이 아예 없다"로 불변식을 세운 것과 같은 수법이고, 그 수법은 이 코드베이스에서
이미 작동하고 있다.

REQ-012 AC-3(탭을 닫으면 정리된다)도 같은 이유로 쉬워진다 — 지울 것이 **한 값**이다.

## 0106 과의 관계

0106 은 **대체되지 않는다.** `ProjectWorkspace.openWorkspace(at:columns:rows:)` 는 그대로 남고,
호출 단위가 "앱"에서 "탭"으로 바뀔 뿐이다. 0106 의 결정·근거는 전부 유효하다.

다만 0106 의 "한계" 절이 여기서 커진다: 엔진 쪽 동작이 바뀌면 이 약속이 조용히 달라질 수 있고,
탭이 여럿이면 **어긋남이 탭 수만큼 생긴다.** 그래서 탭 ↔ Neovim 탭페이지 대응은 앱이 추측하지
않고 **엔진이 알려주는 값을 단일 소스로 쓴다**(ADR-0008 모델 B, 백엔드에 통지 요청 완료).

## 한계

- **Neovim 이 전역으로 두는 상태(레지스터·마크·점프목록)는 탭 간에 공유된다.** ADR-0008 이 모델 B
  를 택한 결과이고, 복사/붙여넣기가 탭을 넘나드는 것은 오히려 기대 동작이라 문제로 보지 않는다.
  **INV-5 의 화면 계약은 `02b §1.1` 표가 정의하는 범위이며, Neovim 전역 상태는 그 표 밖이다.**
- 탭 수에 비례해 메모리가 는다. 이는 사용자가 "전부 유지"를 택한 결과이고, 탭당 증가분은
  ADR-0008 이 실측했다(편집기 약 0.7MB + 인덱스 약 19MB/25,000심볼).
