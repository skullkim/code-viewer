# ADR-0115 — 참조 목록을 수신자 타입으로 좁힌다

**상태:** 채택 (2026-09-06)

## 맥락

참조 검색은 이름으로만 맞춘다. 그런데 이름은 심볼이 아니다.

사용자가 쓰는 463파일 Java 레포에서 실측했다. `getId` 는 **670줄**에 나오고, 그 수신자는
서로 무관한 **15개 타입**으로 갈린다 — `Member` 339, `Organization` 222, `Coupon` 55, 그 외.
`member.getId()` 에 커서를 두고 참조를 열면 프로젝트의 모든 엔티티가 한 목록에 쏟아진다.
사용자의 표현은 "이름만 같고 완전히 다른 애들도 같이 나온다" 였다.

같은 레포에 **이름이 겹치는 클래스는 하나도 없었다.** 즉 문제는 타입이 아니라 메서드·필드다.
클래스 참조는 이미 정확했고, 좁혀야 할 것은 호출부였다.

## 결정

커서가 선 자리의 **수신자 타입**을 알아내고, 그 타입의 호출만 남긴다.

`JavaReceiverType` 이 tree-sitter 로 파일을 읽어 식별자의 **선언된** 타입을 찾는다. 지역 변수,
파라미터, 필드, 향상된 for 변수, `this`, `Type.of(…)` 정적 호출, `Type::method` 메서드 참조까지
다룬다. 선언이 가까운 것부터 이긴다 — 감싸는 메서드 안의 선언이 필드보다 우선한다.

실측: 670건 중 **634건(94.6%)** 의 수신자가 해석된다. `Member` 에 서서 참조를 열면
670 → 363건이 되고, 사라진 267건은 다른 타입의 `getId` 다.

## 가장 중요한 규칙: 모르면 남긴다

판정하지 못한 히트는 **목록에 남긴다.** 이건 타협이 아니라 이 기능의 안전장치다.

두 종류의 실수가 있는데 크기가 다르다. 노이즈 한 줄이 남는 것은 사용자가 보고 넘기면 된다.
진짜 참조가 사라지는 것은 **사용자가 알아챌 방법이 없다** — 목록에 없는 것을 없다고 읽고,
그대로 코드를 고친다. 그래서 확신이 없으면 남기고, 몇 건을 판정 못 했는지 화면에 적는다.

같은 이유로 Java 가 아닌 파일, 읽을 수 없는 파일, 커서 자리에서 타입을 못 알아낸 경우에는
**아무것도 좁히지 않는다**. 좁히기는 켜지거나 꺼지거나이고, 어중간하게 켜지지 않는다.

## 대안

**(1) 그대로 두고 안내 문구로 때운다.** 지금까지의 방식이다. 문구는 이미 있었고("이름 기반
검색 — 동명 이의어 포함 가능") 사용자는 그걸 읽고도 문제를 제기했다. 670줄 목록은 안내가
붙어 있든 없든 쓸 수 없다.

**(2) 언어 서버(JDT)를 붙인다.** 정확도는 최고다. 대신 수백 MB 를 끌고 오고, 그러면 "작고
네이티브"라는 이 앱의 유일한 정당성이 사라진다. Neovim 을 번들하기로 한 ADR-0114 에서
47MB 를 놓고 고민한 앱이 여기서 수백 MB 를 받을 수는 없다.

**(3) 선언 타입만 읽는다 (채택).** 타입 검사기가 아니다. 상속을 따지지 않고, 제네릭 인자를
풀지 않고, 체인 호출의 결과 타입을 모른다. 그 대신 파일 하나를 파싱하는 비용으로 노이즈의
40%를 없앤다 — 그리고 못 하는 것을 화면에서 못 한다고 말한다.

## 결과

- `member.getId()` 참조가 670 → 363건. 다른 엔티티 267건이 사라진다.
- 성능: 파일당 한 번만 파싱한다. 히트마다 파싱하면 670건에 1.59초였고, 지금은 0.24초다.
- 계약이 바뀐다: `ProjectSession.references(to:)` 가 커서 자리(`ReferenceQueryOrigin`)를 받는다.
  기본값을 두지 않았다 — 기본값이 있으면 좁히기를 빠뜨린 호출부가 조용히 생긴다.
- 알려진 한계, 전부 "안 좁힘" 쪽으로 넘어가므로 참조를 지우지는 않는다:
  상속(부모에 선언된 메서드를 자식이 호출하면 다른 타입으로 보인다) · 체인 호출
  (`repo.find().getId()`) · `var` · 제네릭 원소 타입(`list.get(0).getId()`).
- Java 만 좁힌다. Kotlin·TypeScript 는 tree-sitter 강조와 같은 이유로 후속이다.
