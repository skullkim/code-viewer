# ADR-0109: 렌더 보기는 전면 차단 + 앱이 인라인하는 로컬 리소스로 만든다 (INV-6)

- 상태: 채택
- 영역: 프론트엔드 (frontend-senior)
- 날짜: 2026-08-30
- 관련: REQ-013, **INV-6(협상 대상 아님)**, `02b_design.md` D-B · §7.2 · W-15

## 맥락

REQ-013은 임의의 저장소에 있는 `.md`·`.html`을 그리라고 한다. INV-6은 그것이 보안 표면임을
전제로 **원격 리소스 로드 0 · 스크립트 실행 차단 · 로컬 접근을 프로젝트 루트로 제한**을 요구하고,
차단이 기본값이며 완화는 사용자가 명시적으로 요청할 때만이라고 못박았다.

"WKWebView 설정을 잘 하면 되겠지"는 가정이고, **틀리면 렌더 표면 설계가 통째로 바뀐다.**
그래서 구현 전에 스파이크로 실측했다(§3.6 선행 검증).

## 실측 (2026-08-30, `scripts/spike-render-sandbox.swift`)

로컬 리스너를 띄우고 stylesheet·script·img·`@font-face`·인라인 스크립트의 `Image()`·`fetch()`
여섯 경로를 건 페이지를 로드해, **연결이 실제로 오는지**로 판정했다.

| 변종 | 원격 요청 | 인라인 스크립트 |
|---|---|---|
| **대조군** (JS 켬, 규칙 없음) | 다수 (`style.css`·`script.js`·`image.png`·`font.woff`·`from-inline-script`·`from-fetch`) | 실행됨 |
| **JS만 끔** (규칙 없음) | **9건** — `style.css`·`image.png`·`font.woff` 그대로 나감 | 실행 안 됨 |
| **규칙(`.*` block) + JS 끔** | **0건** | 실행 안 됨 |

**대조군을 먼저 통과시킨 뒤에 0을 읽었다.** 그 순서가 아니면 0은 "막았다"와 "리스너가 고장났다"를
구별하지 못한다.

**여기서 나온 가장 중요한 사실: `allowsContentJavaScript = false` 는 네트워크를 막지 않는다.**
스크립트 실행만 막는다. `<img>`·`<link>`·`@font-face`는 그대로 나간다(9건). 차단을 실제로 하는
것은 **`WKContentRuleList` 하나**다. 이 구분을 모른 채 "JS 껐으니 안전하다"고 두면 INV-6의 첫
항목이 조용히 열린다.

### 규칙 목록의 제약 (실측)

- **커스텀 스킴은 `.*` 에 함께 막힌다.** `WKURLSchemeHandler` 를 붙여도 핸들러 호출 **0건**.
- **`ignore-previous-rules` 로 되살릴 수 없다.** `^cnres://` 허용 규칙을 더해도 여전히 0건.
- **정규식에 분기(`|`)를 못 쓴다.** `^(https?|wss?|ftp|file)://` 는
  `Disjunctions are not supported yet` 로 컴파일 실패한다.
- **`data:` URI 는 `.*` 차단 아래에서도 살아 있다.** 화면 밖 창에 담아 스냅샷의 가운데 픽셀을
  재니 `rgb(220,50,47)` — 의도한 색 그대로다. 깨진 `data:` 로 같은 측정을 하면
  `rgb(153,195,226)`(깨진 이미지 자리표시자)이 나온다. **검사기가 둘을 구별한다는 것까지 확인했다.**

## 결정

**세 겹으로 만든다.**

1. **전면 차단이 기본값** — `WKContentRuleList` 가 `.*` 를 block 한다. 스킴을 열거하지 않는다.
2. **로컬 리소스는 앱이 읽어 `data:` 로 인라인한다** — 렌더 표면은 파일 시스템에 닿지 않는다.
   루트 제한은 우리 코드가 하고, 우리 코드는 테스트할 수 있다.
3. **스크립트 실행 차단** — `allowsContentJavaScript = false`. 1번이 이미 외부 스크립트를 막지만,
   인라인 스크립트는 네트워크를 안 쓰고도 DOM 을 바꿀 수 있으므로 별도로 끈다.

**실패는 닫히는 쪽으로.** 규칙 목록은 **비동기로 컴파일**된다. 컴파일이 끝나 규칙이 붙기 전에는
어떤 내용도 로드하지 않고, 컴파일이 실패하면 **렌더를 거부하고 그 사실을 화면에 말한다**(W-15).
차단이 없는 채로 그리는 경로를 코드에 두지 않는다 — 그 경로는 반드시 언젠가 실행된다.

**마크다운도 같은 표면을 지난다.** 마크다운 → HTML → 같은 샌드박스다. INV-6이 "마크다운도
같다"고 한 이유가 마크다운이 HTML 을 품기 때문이고, 표면을 둘로 나누면 **보안 경계도 둘**이 된다.

## 고려한 대안

**A. 스킴 열거 차단** (`http`·`https`·`ws`·`wss`·`ftp`·`file` 각각 block 규칙)
커스텀 스킴 핸들러로 로컬 리소스를 서빙할 수 있어 인라인이 필요 없다. 그러나 **분기 정규식이
안 되므로 스킴마다 규칙을 하나씩** 써야 하고, 그것은 곧 **빠뜨린 스킴이 열린다**는 뜻이다.
보안 표면에서 열거 방식은 "내가 생각해낸 것만 막는다"와 같은 말이다. INV-6이 "차단이
기본값"이라고 쓴 것은 이 선택을 배제한 문장으로 읽는 게 맞다.

**B. WebView 없이 네이티브 렌더** (마크다운은 `AttributedString`)
가장 안전하다 — 그릴 수 있는 것이 우리가 만든 것뿐이다. 그러나 **REQ-013 AC-2가 `.html` 을
요구**하고, HTML 렌더러를 직접 만드는 것은 이 빌드의 범위를 한참 넘는다. 마크다운만 네이티브로
하면 표면이 둘이 되고 **보안 경계도 둘**이 된다 — 그중 하나만 틀려도 INV-6은 깨진다.

**C. 전면 차단 + `data:` 인라인 (채택)**

## 트레이드오프

- **테스트 용이성**: C 는 루트 제한이 **우리 코드의 순수 함수**가 된다("이 경로가 루트 안인가").
  A 는 그 판정이 스킴 핸들러 안에 있고, 그것을 테스트하려면 WebView 를 띄워야 한다.
- **단순성**: A 가 큰 문서에서 유리하다 — C 는 이미지를 base64 로 부풀려(약 4/3배) HTML 에
  싣는다. 그래서 **2MB 상한**(§12 판정 6)이 이 결정과 맞물린다. 상한에 걸리면 조용히 자르지 않고
  무엇이 왜 안 보이는지 말한다.
- **변경 가능성**: 완화 요청(INV-6은 "사용자가 명시적으로 요청할 때만")이 실제로 오면, C 는
  규칙 목록을 교체하는 한 곳만 바뀐다.
- **되돌림**: 세 겹 중 어느 것도 다른 곳에 스며들지 않는다. 렌더 표면 하나에 갇혀 있다.

## 채택 이유

**틀렸을 때 조용한 쪽을 피한다.** 열거 차단(A)이 틀리면 증상이 없다 — 사용자가 신뢰하지 않는
저장소를 열었고 무언가 밖으로 나갔지만 화면은 멀쩡하다. 전면 차단(C)이 틀리면 **로컬 이미지가
안 보인다** — 즉시 눈에 띄고, 고칠 수 있고, 아무것도 새지 않는다.

INV-6이 협상 대상이 아니라고 명시된 이상, 실패 모드가 시끄러운 쪽을 고르는 것이 맞다.

## 추가 실측 — `data:` 는 무조건 통과가 아니다 (리더 판정)

이 ADR 의 초판은 `data:` 를 전부 통과시켰다. **틀렸다.** 리더 판정으로 좁혔다:

| | |
|---|---|
| `data:image/png` · `jpeg` · `gif` · `webp` | **허용** — 네트워크에도 실행에도 안 닿는다 |
| `data:image/svg+xml` | **차단** — SVG 는 마크업이고 스크립트를 품는다. `<img>` 안에서 그것이
무해한지는 **렌더러 구현에 달려 있고, 그건 우리가 통제하는 전제가 아니다** |
| 그 외 모든 `data:` | **차단** |

그리고 **자리도 본다** — 같은 래스터 `data:` 라도 이미지 자리에서만 허용하고 스타일시트·폰트
자리에서는 차단한다. 판정은 "이미지"에 대한 것이었고, 인접한 자리로 넓히는 것이 스코프 크리프의
조용한 형태다.

**스크립트와 프레임은 위치와 무관하게 차단한다.** INV-6 이 막는 것은 *실행*이고, 루트 안의
스크립트도 루트 밖의 것과 똑같이 실행된다.

## 추가 실측 — 경로 해석이 조용히 생략된다 (D-12)

**`URL.resolvingSymlinksInPath()` 는 leaf 가 존재하지 않으면 심링크를 풀지 않는다.** 백엔드가
발견하고 리더가 독립 재현했으며, 나도 고친 뒤 양방향으로 재확인했다.

```
leaf 존재   link/exists.md → 차단 ✅
leaf 부재   link/later.md  → 차단 ✅   (수정 전: 미해석 경로가 접두 비교를 통과해 허용 ❌)
leaf 부재   link/a/b.md    → 차단 ✅
양성 대조   img/logo.png   → 허용 ✅   (과차단이 아니다)
양성 대조   루트 안 심링크  → 허용 ✅
```

**주석은 "양쪽 다 해석하고 비교한다"고 정확히 적혀 있었고 구현이 그 약속을 조건부로만 지켰다.**
그래서 해석은 `realpath(3)` 으로 한다 — 존재하지 않으면 `NULL` 을 돌려주므로 **해석할 수 없는
경로는 자동으로 차단**된다(fail closed). 그리고 **검사한 경로가 아니라 해석된 경로를 돌려주고
그것을 읽는다** — 검사와 로드 사이에 링크가 바뀌는 창(TOCTOU)까지 닫힌다.

**문자열 픽스처로는 영원히 안 잡힌다.** 실제 심링크를 만들어야 하고, **leaf 가 있는 경우와 없는
경우를 둘 다** 넣어야 한다 — 있는 케이스만 두면 통과한다.

## 결과 (구현 시 지킬 것)

- **규칙이 붙기 전에 로드하지 않는다.** 컴파일 실패 = 렌더 거부(빈 화면 금지 — AC-6·W-15).
- **루트 제한은 `RenderSandboxPolicy` 한 곳에 둔다.** 한때 같은 판정이 두 파일에 있었고
  (`RenderResourcePolicy` — 폐기), **보안 경계에 진실이 둘인 상태**였다. 남긴 쪽이 `02b` W-15 가
  요구하는 **요소 종류 축**(원격 이미지·스크립트·원격 스타일시트·원격 폰트·프레임·프로젝트 밖
  파일 6분류)을 갖는다 — 그 축이 없으면 차단 팝오버가 "원격 3건"으로 뭉개져, 무엇이 빠졌는지
  세라는 W-15 의 목적이 사라진다.
- **정체성 판정과 보안 판정은 구현을 공유하지 않는다.** 한때 `ProjectIdentity.canonical` 이
  *"두 경로가 같은 프로젝트인가"* 와 *"이 경로가 루트 안인가"* 를 겸했다. **둘은 해석에 실패했을 때
  정반대로 행동해야 한다** — 정체성은 관대해도 되고 **보안은 차단**이어야 한다. 겸하면 한쪽 요구로
  고칠 때 다른 쪽이 조용히 바뀐다. 공유할 것은 구현이 아니라 계약이다.
- **차단한 것을 세어 화면에 말한다**(W-15 `🛡 차단됨 n`). 조용히 비우면 사용자는 앱이 고장난
  것으로 읽는다. 목록은 **렌더 결과와 함께 한 번에** 받는다(`02b §11-6`).
- **이 결정이 지켜지는지 확인하는 곳**: `scripts/spike-render-sandbox.swift` 를 회귀 검사로
  승격한다 — 대조군(요청이 와야 한다)과 차단군(0이어야 한다)을 **양방향으로** 돌린다. 한쪽만
  도는 검사는 리스너가 죽어도 초록이다.
