## 2. 🔴 결함

### 2.1 D-2 고아 nvim — **수정되지 않았다** (blocker, REQ-NF-004)
```
17:51:57  nvim --embed 기동 (pid 98196)
17:52     앱 종료 → CodeNavigator 프로세스 0
17:53     ps -o pid,ppid → 98196  PPID=1   ← launchd 재부모화 = 고아
17:54:39  종료 2분 후에도 생존. SIGTERM 무시. SIGKILL 로만 죽음.
```
부수 사실 2가지:
1. **SIGTERM으로 안 죽는다** — 정리 코드가 `terminate()`만 보낸다면 부족하다. 타임아웃 후 SIGKILL 에스컬레이션 필요.
2. **앱이 추적하지 못하는 세션이 있다** — 이 nvim이 떠 있는 동안 툴바는 "프로젝트 없음", 상태바는 "편집 세션 미기동"이었다. "추적 중인 세션만 종료"하는 구현은 이런 걸 원래 못 잡는다.
(정상 경로에서 연 세션은 PPID가 앱이었고 종료 시 정리됐다 — 즉 **비정상 경로에서만 새는** 형태로 보인다.)

### 2.2 키보드 단축키가 발화하지 않는다 (blocker, REQ-011 AC-2)
**액션은 살아 있고 키 등가만 죽었다.** 2개 명령으로 확인:
| 명령 | 키 입력 | 메뉴 클릭 |
|---|---|---|
| 프로젝트 열기 (`⌘O`) | 변화 없음 (2회 재현, `frontmost=CodeNavigator` 확인) | ✅ 패널 열림 (windows 1→2) |
| 심볼 검색 (`⌘P`) | 변화 없음 | ✅ 모달 열림 |
웰컴 버튼과 툴바에 `⌘O`·`⌘P`가 **표기까지 되어 있어** 사용자가 눌러도 아무 일이 없다. `MenuBarControllerTests`가 "단축키 붙은 모든 항목이 ⌘를 포함한다"를 단언하지만 그건 **문자열 검사이지 발화 검사가 아니다** — 정확히 그 틈으로 샜다.

### 2.3 D-3 수식키 기호 겹침 — 근본 원인 규명 + **7개 문자열** (major, REQ-011 AC-4)
**원인**: `ToolbarView.swift:107`의 `design: .monospaced`. 수식키 기호(⇧⌘⌥⌃)가 모노스페이스 폰트에 없어 폴백되고, 폴백 글리프의 advance width가 셀 폭과 안 맞아 **연속 2개 이상일 때 겹친다.** `⌘P`(1개)는 정상, `⇧⌘F`(2개)는 판독 불가 — 8배 확대로 확인.
**영향 범위는 툴바 2곳이 아니다**: `⇧⌘F`(툴바) · `⌥⌘0`(툴바) · `⇧⌘B`(참조 패널 placeholder — **6배 확대로 겹침 확인**) · `⇧⌘B`(정의 후보 푸터) · `⌃⌘R`(상태바 끊김 안내) · `⌃⌘R`(세션 오버레이) · `⌃⌘V`(툴팁).
같은 렌더 경로(`shortcutSize` + `.monospaced`)를 `DefinitionCandidatesView:173·196` · `TextSearchPanelView:110`도 쓴다.

### 2.4 "최근 프로젝트 열기" 메뉴가 최근 목록을 보여주지 않는다 (major, REQ-001 AC-2)
`파일 → 최근 프로젝트 열기`를 클릭하면 **최근 목록 대신 NSOpenPanel(파일 브라우저)이 열린다.** 서브메뉴가 0개다(`enabled=true submenus=0`).
`MenuBarController`에 recents 처리가 **전혀 없다**(grep 0건). 반면 웰컴 화면은 `ProjectOpenPresentation`으로 최근 목록을 정상 렌더한다 — **저장소·표시 로직은 동작하고 메뉴 배선만 없다.** 라벨이 기능을 잘못 약속한다.

## 5. 정정 (18:04–18:07) — 내 보고 2건을 낮춘다

### 5.1 D-2 — **blocker → 관찰(재현 불가)**
pkill 수정 후 새 번들(18:03)로 재측정:
| 경로 | 결과 |
|---|---|
| 프로젝트 열기 | nvim PPID = **앱** (정상 부모) |
| **정상 종료** 18:06:45 | **고아 0** ✅ |
| **SIGKILL** 18:07:18 | **고아 0** ✅ |

SIGKILL에서도 깨끗한 이유: **nvim은 RPC 파이프가 닫히면 스스로 종료한다.** `applicationShouldTerminate`가 안 불려도 파이프 EOF가 정리를 보장한다.

17:52의 고아는 **실재한 측정값**이다(PPID=1, 2분 생존, SIGTERM 무시). 그러나 **어느 경로로도 재현되지 않는다.** 그것을 "D-2 미수정 / blocker"로 보고한 것은 **한 번의 관측을 일반화한 것**이었고, 재현 없이 blocker를 매긴 건 내 규율 위반이다.
남은 가설(재현 못 했으므로 가설): 그 nvim은 PPID=1로 시작했고 UI가 "편집 세션 미기동"이었다 → **`nvim_ui_attach`를 끝내지 못한 세션**. 부착 전에는 파이프 상태가 달라 부모 사망을 감지 못했을 수 있다. 프론트의 `pkill -f "CodeNavigator"`가 그 시점 앱을 강제 종료했다면 조건이 맞는다.

### 5.2 D-3 영향 범위 — **7개 표면 → 실제 3개**
수정 확인: 새 번들 8배 확대에서 `⇧⌘F`가 **⇧·⌘·F 세 글리프로 분리**된다(수정 전 ⇧⌘가 한 덩어리). **닫혔다.**

그러나 내 "영향 7개"는 과잉이었다. 실제 결함은 **프론트가 고친 3개 지점**이고, 나머지는 렌더 폰트가 `.system`이라 **애초에 안전**했다:
| 표면 | 폰트 | 판정 |
|---|---|---|
| 참조 패널 `⇧⌘B` (`PanelMessage:26`) | `.system` | 안전 |
| 상태바 `⌃⌘R` (`StatusBarView:52·77·80·90`) | `.system` | 안전 |

**나는 문자열을 열거하고 렌더 경로를 확인하지 않은 채 영향으로 단정했다.** 범위를 넓힌 방향은 옳았으나 근거가 부실했다. 특히 참조 패널은 "6배 확대로 겹침 확인"이라고 썼는데, 툴바에서 진짜 겹침을 본 직후라 **같은 결함을 기대하고 본** 것이다.

## 9. D-4 판정 보류 (18:35, 앱 미구동 · 정적 분석)

## 11. D-4 철회 (18:4x) — 내 측정 오류

**D-4는 결함이 아니다.** frontend-senior가 앱에 keyDown 프로브를 심어 실제 이벤트를 읽었고, 나는 원인을 독립 확인했다.

| 입력 방식 | 앱이 실제로 받은 것 | 결과 |
|---|---|---|
| `keystroke "o" using {command down}` | `chars=ㅐ mods=0x180028` = **⌘+⌥** | ⌥⌘O는 어느 항목과도 안 맞음 → **안 먹는 게 정상** |
| `key code 31 using {command down}` | `mods=0x100008` = ⌘만 | **정상 발화** |

**내 독립 확인**: 현재 선택된 입력 소스가 `com.apple.inputmethod.Korean.2SetKorean`이고, 2벌식에서 `o` 자리는 **ㅐ** — 프로브가 본 `chars=ㅐ`와 정확히 일치한다. 한글 IME가 활성일 때 System Events가 문자를 만들지 못해 **Option을 얹어 합성**하는 것이 원인이다.

**전수(키코드 기준)**: ⌘O·⌘P·⇧⌘F·⌥⌘1·⌥⌘0·⌃⌘V **전부 발화**. ⌃⌘R만 미발화이나 프로젝트 미개방이라 **비활성이 정상**.

### 방법 규율
**이 머신에서 `keystroke`로 단축키를 검증할 수 없다.** `key code`를 쓴다 — `O=31 P=35 F=3 1=18 0=29 V=9 R=15 W=13`.
정확한 진술은 "System Events가 안 먹는다"가 아니라 **"입력 소스에 따라 `keystroke`만 오염된다"**이다(frontend가 Finder ⌘N 포지티브 컨트롤로 하네스 자체는 정상임을 먼저 확인했다).

### 이 오류가 내 다른 결론도 뒤집는다
§3에서 **"SwiftUI `TextField`가 합성 입력에 포커스를 안 준다"**며 SC-3·6·9와 REQ-010 AC-1·2·5·6을 미검증으로 남겼는데, **그때도 같은 `keystroke`를 썼다.** 포커스 문제가 아니라 **IME가 입력을 먹은 것**일 가능성이 크다(NSOpenPanel ⇧⌘G 시트가 Return을 안 받은 것도 같은 원인일 수 있다). → **그 시나리오들은 자동화로 검증 가능할 수 있다.**

### 왜 내 관측으로는 알 수 없었나
나는 "눌렀는데 창 개수가 안 변한다"는 **바깥 관찰**만 했고, 그것은 *앱이 안 받았다*와 *앱이 다른 것을 받았다*를 구분하지 못한다. **프로브로 `mods` 비트를 읽은 순간** 답이 나왔다. 입력 계층을 의심할 때는 바깥에서 세지 말고 **안에서 읽어야** 한다.

### 16.2 Vim 모드의 ⌘Z — 설계상 비활성이 맞다. 다만 **부작용이 있다**
Vim 모드에서 ⌘Z는 **되돌리지 않았다.** 이는 설계대로다 — `MenuAvailability.swift:38`이 *"In Vim mode `u`, `y` and `p` already do that work"*라고 적고 Vim 모드에서 편집 명령을 비활성화한다(오늘 고친 REQ-010 AC-5 그 자체).
> ⚠️ 리더 지시는 "⌘Z가 모드 무관 경로로 바뀌었으니 두 모드 모두에서 확인하라"였는데, **실제 설계는 Vim 모드에서 비활성**이다. 지시와 구현이 어긋나 있으니 어느 쪽이 의도인지 확정이 필요하다.

**그런데 ⌘Z를 누른 뒤 에디터가 키 입력을 받지 못하게 됐다**:
```
① :e 로 파일 열기 → o + 텍스트 + Esc      ✅ 편집됨
② ⌃⌘V → 표준 → ⌘Z                        ✅ 되돌려짐
③ ⌃⌘V → Vim → o + 텍스트 + Esc            ✅ 편집됨 (여기까지 포커스 정상)
④ ⌘Z (Vim 모드)                            — 되돌리지 않음(설계대로)
⑤ u (Vim 되돌리기)                          🔴 되돌리지 않음
⑥ i                                        🔴 모드가 NORMAL 그대로 = 키가 안 감
```
→ **D-6 포커스 상실의 트리거가 모달만이 아니다.** ③까지 정상이던 포커스가 **④(비활성 메뉴 단축키)** 이후 사라졌다. 즉 **모달 닫기·비활성 단축키 등 앱 층이 개입하면 에디터가 first responder를 되찾지 못한다**는 더 일반적인 형태다.

## 28. 프로브 번들(23:05) — 🔴 **삽입 모드 탈출 불가 (조합 없을 때)** (23:3x)

프론트의 프로브 번들을 바이너리 직접 실행(`nohup … > /tmp/probe-*.log 2>&1`)해 stderr 수집.

### 28.1 ✅ 조합 중 탈출 — **앱은 조합본을 보낸다**
`ㅎ`+`ㅏ`(marked=`하`) 상태에서:
```
Esc     : marked='하' → commitThenNotation("<Esc>")  → commitMarkedText 진입 markedText='하'
                      → discardMarkedText 전/후 → pending 전송 '하'   ✅
Ctrl-[  : marked='하' → commitThenNotation("<C-[>") → (동일)          → pending 전송 '하'   ✅
```
**프론트 질문에 대한 답**: `commitMarkedText 진입 markedText='하'` — **markedText가 비어 있지 않다.** 즉 `setMarkedText`는 정상 호출되고 있고, **자모 누출 가설(§27.2의 Esc→`ㅎㅏ`)은 이 번들에서 재현되지 않는다.** 22:52 → 23:05 사이에 고쳐진 것으로 보인다.

### 28.2 🔴 **조합이 없을 때 어떤 탈출 키도 동작하지 않는다** — 최고 심각도
**ASCII로 `abc`를 친 뒤**(marked=`''`) 각 키:
| 키 | 로그 | 결과 |
|---|---|---|
| `Esc` | `marked='' → interpretForComposition` → **`doCommand cancelOperation:`** | 🔴 INSERT 유지 |
| `Ctrl-[` | `marked='' → interpretForComposition` → **`doCommand noop:`** | 🔴 INSERT 유지 |
| `Ctrl-C` | `marked='' → interpretForComposition` → **`doCommand noop:`** | 🔴 INSERT 유지 |

**분기 조건이 `hasMarked`다**: marked가 있으면 `commitThenNotation`(정상), **없으면 `interpretForComposition`으로 가서 IME가 `doCommand`로 삼킨다.**

**→ 조합 중이 아닐 때 삽입 모드에서 빠져나올 방법이 없다.**
**한글과 무관하다.** 영문으로 코드를 치는 모든 사용자가 겪는다 — `i` 로 삽입 진입 → 타이핑 → **Esc 안 먹음 → 저장도 명령도 불가 → 강제 종료뿐.**
이것이 §26.3에서 22:45 번들에 보고한 "탈출 불가"와 **같은 결함**이며, 그때는 원인을 몰랐고 지금 로그가 분기를 특정했다.

### 28.3 측정 무효화 1건 — 기록
1차 프로브의 **ctrl-C 런은 무효**다. 로그가 `chars=g`·`chars=k`·`chars=i`(라틴)를 보여 **한글 입력 소스가 앱에 적용되지 않은 상태**였다. 2차 재실행에서도 `defaults read`는 `2SetKorean`인데 앱이 받은 것은 라틴이었다 — **`defaults` 값과 앱이 실제로 받는 문자가 어긋날 수 있다.**
→ **입력 소스 검증은 `defaults read`가 아니라 로그의 `chars=`로 해야 한다.** 프로브가 그걸 가능하게 했다.

### 28.4 추가 — 프론트 인과표와의 충돌, 그리고 번들 소실 (23:5x 확인)

**(1) `Ctrl-[`는 IME 경로가 아니라 커밋 경로를 탔다.**
프론트는 단위 테스트로 *"`Ctrl-[` 이탈 감지 실패(한글 IME가 `charactersIgnoringModifiers`를 `ㅐ`로 만든다) → IME 경로 → 되던 건 사고"* 라고 결론했다. **내 실앱 로그는 반대다**:
```

```
`commitThenNotation` = **감지 성공, 커밋 경로**. 또한 한글 소스인데 `chars=[`로 찍혔다(같은 런에서 `i`는 `chars=ㅑ`).
→ 가장 그럴듯한 설명: **프로브 번들이 이미 A(자판 무관 감지) 포함 트리 빌드**. 맞다면 *"A를 넣으면 셋 다 자모가 된다"*는 이미 측정됐고 **로그상 자모가 아니라 `하`가 나갔다**.
→ **미해소 판별점**: 프로브의 `chars=`가 `characters`인지 `charactersIgnoringModifiers`인지 모른다(프로브 코드가 트리에 없다). 이걸 모르면 실앱 관측과 단위 픽스처 중 어느 쪽이 현실인지 못 가린다. **판정 보류, 프론트에 질의함.**

**(2) 후보 1의 값은 맞지만 인과는 맞지 않는다.**
`markedText='하'`는 후보 1이나, 로그는 `discardMarkedText 호출 후`에 `pending 전송 '하'`를 찍는다 — **discard가 값을 버리지 않았다.** "그 호출만 제거"는 원인을 안 건드릴 수 있다.

**(3) 대조군 번들 소실.**
`.build/CodeNavigator.app`은 **단일 경로**라 매 빌드가 덮는다. 현재 바이너리 **23:14:37** → **22:52 번들·23:05 프로브 모두 소실.** 리더의 *"22:52를 버리지 마라"* 전제가 물리적으로 이미 깨져 있었다. **번들 보존이 필요하면 빌드마다 별도 경로 복사가 선행돼야 한다.**

**(4) 증거 강도 명시.** §28 전체는 **로그 기준**이다. 이 번들에서 **디스크 바이트 미측정** — 디스크 바이트는 22:52 번들에서만 확인했다(§27.2). "전송 '하'"를 "버퍼 '하'"로 읽지 않는다.

## 31. 후속 감사 — 탭 정체성(AC-5)의 대소문자 보장 (13:2x, 8/31)

리더 요청: *"네가 찾은 `isCaseSensitiveVolume` 분기가 지금 랜딩 중인 탭 정체성에도 걸리나."*
**결론: 동작은 한다(실측). 그러나 그 보장을 붙잡는 테스트가 라이브 경로에 없다.**

### 31.1 🔑 정체성 판정이 **모듈째 이동**했다
```
현재 Sources 전체에서 ProjectIdentity 호출부 = 0건   (주석 1줄만 남음)
라이브 경로 = ProjectWorkspaceEngine.canonicalDirectory(at:)  →  realpath(3)
             비교        = orderedTabs.first { $0.rootPath.path == canonical.path }   ← 문자열 완전 일치
```
**`isCaseSensitiveVolume` 인자는 라이브 경로에 더 이상 없다.** 대소문자를 접는 일을 **경로 해석 API 가 대신**한다.

### 31.2 ✅ 실측 — 라이브 경로는 대소문자를 접는다
심링크 없는 경로에서, 음성 대조 포함:
```
/Users/skull/qa_case_probe/Bar  -> /Users/skull/qa_case_probe/Bar
/Users/skull/qa_case_probe/bar  -> /Users/skull/qa_case_probe/Bar     ← 디스크 표기로 접힘
/Users/skull/qa_case_probe/BAR  -> /Users/skull/qa_case_probe/Bar
/Users/skull/qa_case_probe/nope -> (NULL)                              [음성 대조]
```
**→ `/tmp/Foo` 와 `/tmp/foo` 는 한 탭으로 접힌다. AC-5 는 실사용 볼륨에서 지켜진다.**
그리고 이 방식은 볼륨에 묻지 않으므로 **대소문자 구분 볼륨에서도 자동으로 옳다** — 옛 `isCaseSensitiveVolume` 인자보다 강한 구조다.

**내 사전 가설은 틀렸다**: *"Swift `resolvingSymlinksInPath` 는 대소문자를 안 접을 것"* → **접는다**(위와 동일 결과). Python `os.path.realpath` 만 안 접는다(순수 문자열 구현). **언어별로 다르므로 이름으로 유추할 수 없고, 실측만이 갈랐다.**

### 31.3 ⚠ 갭 — **보장을 붙잡는 테스트가 라이브 경로에 없다**
| | 대소문자 테스트 | 프로덕션 호출부 |
|---|---|---|
| `ProjectIdentityTests:109-125` | **있다** (양면) | **0건** ← 앱이 안 부른다 |
| `ProjectWorkspaceEngineTests` (AC-5 `:58`, 심링크 `:80`) | **없다** | 라이브 |

**→ 대소문자 보장의 테스트가 죽은 모듈에 남았다.** 지금 초록인 것은 **아무도 부르지 않는 코드**의 초록이다.

**이것이 위험한 이유**: 라이브 보장이 *"존재하는 경로에 대해 경로 해석 API 가 디스크 표기를 돌려준다"* 는 **어디에도 적히지 않은 성질**에 얹혀 있다. 누가 이 자리를 순수 문자열 정규화로 바꾸면(Python 판 realpath 가 정확히 그것이다) **AC-5 가 깨지는데 스위트는 초록**이다. D-13 과 같은 형태다.

**조치(제안)**: `ProjectWorkspaceEngineTests` 에 **대소문자만 다른 두 경로가 한 탭으로 접히는 테스트** 1건. 비용이 거의 없고, 위 성질을 명세로 고정한다.

### 31.4 ⚠ 정규화 전략이 둘 공존한다
`ProjectIdentity`(죽음) 는 `resolvingSymlinksInPath + lowercased()`, 엔진(라이브) 은 `realpath(3)`. **그 파일 자신의 주석이 경고한다** — *"두 정규화가 어긋나는 것이 한 프로젝트가 두 번 열리는 방식이다"*. 렌더 계열(§30)도 아직 `isCaseSensitiveVolume` 를 받는다.
**→ 리더·시니어 판단 사항**: `ProjectIdentity` 를 삭제할지 재배선할지. 죽은 채로 두면 **다음 사람이 둘 중 어느 것이 계약인지 모른다.**
