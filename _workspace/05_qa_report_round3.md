## 2. 🔴 결함

### 2.1 D-2 고아 nvim — **수정되지 않았다** (blocker, REQ-NF-004)
```
17:51:57  nvim --embed 기동 (pid 98196)
17:52     앱 종료 → CodeNavigator 프로세스 0
17:53     ps -o pid,ppid → 98196  PPID=1   ← launchd 재부모화 = 고아
17:54:39  종료 2분 후에도 생존. SIGTERM 무시. SIGKILL 로만 죽음.
```
부수 사실 2가지:
1. **SIGTERM으로 안 죽는다** — 정리 코드가 `terminate()`만 보낸다면 부족하다. 타임아웃 후 SIGKILL 에스컬레이션 필요.
2. **앱이 추적하지 못하는 세션이 있다** — 이 nvim이 떠 있는 동안 툴바는 "프로젝트 없음", 상태바는 "편집 세션 미기동"이었다. "추적 중인 세션만 종료"하는 구현은 이런 걸 원래 못 잡는다.
(정상 경로에서 연 세션은 PPID가 앱이었고 종료 시 정리됐다 — 즉 **비정상 경로에서만 새는** 형태로 보인다.)

### 2.2 키보드 단축키가 발화하지 않는다 (blocker, REQ-011 AC-2)
**액션은 살아 있고 키 등가만 죽었다.** 2개 명령으로 확인:
| 명령 | 키 입력 | 메뉴 클릭 |
|---|---|---|
| 프로젝트 열기 (`⌘O`) | 변화 없음 (2회 재현, `frontmost=CodeNavigator` 확인) | ✅ 패널 열림 (windows 1→2) |
| 심볼 검색 (`⌘P`) | 변화 없음 | ✅ 모달 열림 |
웰컴 버튼과 툴바에 `⌘O`·`⌘P`가 **표기까지 되어 있어** 사용자가 눌러도 아무 일이 없다. `MenuBarControllerTests`가 "단축키 붙은 모든 항목이 ⌘를 포함한다"를 단언하지만 그건 **문자열 검사이지 발화 검사가 아니다** — 정확히 그 틈으로 샜다.

### 2.3 D-3 수식키 기호 겹침 — 근본 원인 규명 + **7개 문자열** (major, REQ-011 AC-4)
**원인**: `ToolbarView.swift:107`의 `design: .monospaced`. 수식키 기호(⇧⌘⌥⌃)가 모노스페이스 폰트에 없어 폴백되고, 폴백 글리프의 advance width가 셀 폭과 안 맞아 **연속 2개 이상일 때 겹친다.** `⌘P`(1개)는 정상, `⇧⌘F`(2개)는 판독 불가 — 8배 확대로 확인.
**영향 범위는 툴바 2곳이 아니다**: `⇧⌘F`(툴바) · `⌥⌘0`(툴바) · `⇧⌘B`(참조 패널 placeholder — **6배 확대로 겹침 확인**) · `⇧⌘B`(정의 후보 푸터) · `⌃⌘R`(상태바 끊김 안내) · `⌃⌘R`(세션 오버레이) · `⌃⌘V`(툴팁).
같은 렌더 경로(`shortcutSize` + `.monospaced`)를 `DefinitionCandidatesView:173·196` · `TextSearchPanelView:110`도 쓴다.

### 2.4 "최근 프로젝트 열기" 메뉴가 최근 목록을 보여주지 않는다 (major, REQ-001 AC-2)
`파일 → 최근 프로젝트 열기`를 클릭하면 **최근 목록 대신 NSOpenPanel(파일 브라우저)이 열린다.** 서브메뉴가 0개다(`enabled=true submenus=0`).
`MenuBarController`에 recents 처리가 **전혀 없다**(grep 0건). 반면 웰컴 화면은 `ProjectOpenPresentation`으로 최근 목록을 정상 렌더한다 — **저장소·표시 로직은 동작하고 메뉴 배선만 없다.** 라벨이 기능을 잘못 약속한다.

## 5. 정정 (18:04–18:07) — 내 보고 2건을 낮춘다

### 5.1 D-2 — **blocker → 관찰(재현 불가)**
pkill 수정 후 새 번들(18:03)로 재측정:
| 경로 | 결과 |
|---|---|
| 프로젝트 열기 | nvim PPID = **앱** (정상 부모) |
| **정상 종료** 18:06:45 | **고아 0** ✅ |
| **SIGKILL** 18:07:18 | **고아 0** ✅ |

SIGKILL에서도 깨끗한 이유: **nvim은 RPC 파이프가 닫히면 스스로 종료한다.** `applicationShouldTerminate`가 안 불려도 파이프 EOF가 정리를 보장한다.

17:52의 고아는 **실재한 측정값**이다(PPID=1, 2분 생존, SIGTERM 무시). 그러나 **어느 경로로도 재현되지 않는다.** 그것을 "D-2 미수정 / blocker"로 보고한 것은 **한 번의 관측을 일반화한 것**이었고, 재현 없이 blocker를 매긴 건 내 규율 위반이다.
남은 가설(재현 못 했으므로 가설): 그 nvim은 PPID=1로 시작했고 UI가 "편집 세션 미기동"이었다 → **`nvim_ui_attach`를 끝내지 못한 세션**. 부착 전에는 파이프 상태가 달라 부모 사망을 감지 못했을 수 있다. 프론트의 `pkill -f "CodeNavigator"`가 그 시점 앱을 강제 종료했다면 조건이 맞는다.

### 5.2 D-3 영향 범위 — **7개 표면 → 실제 3개**
수정 확인: 새 번들 8배 확대에서 `⇧⌘F`가 **⇧·⌘·F 세 글리프로 분리**된다(수정 전 ⇧⌘가 한 덩어리). **닫혔다.**

그러나 내 "영향 7개"는 과잉이었다. 실제 결함은 **프론트가 고친 3개 지점**이고, 나머지는 렌더 폰트가 `.system`이라 **애초에 안전**했다:
| 표면 | 폰트 | 판정 |
|---|---|---|
| 참조 패널 `⇧⌘B` (`PanelMessage:26`) | `.system` | 안전 |
| 상태바 `⌃⌘R` (`StatusBarView:52·77·80·90`) | `.system` | 안전 |

**나는 문자열을 열거하고 렌더 경로를 확인하지 않은 채 영향으로 단정했다.** 범위를 넓힌 방향은 옳았으나 근거가 부실했다. 특히 참조 패널은 "6배 확대로 겹침 확인"이라고 썼는데, 툴바에서 진짜 겹침을 본 직후라 **같은 결함을 기대하고 본** 것이다.

## 9. D-4 판정 보류 (18:35, 앱 미구동 · 정적 분석)

## 11. D-4 철회 (18:4x) — 내 측정 오류

**D-4는 결함이 아니다.** frontend-senior가 앱에 keyDown 프로브를 심어 실제 이벤트를 읽었고, 나는 원인을 독립 확인했다.

| 입력 방식 | 앱이 실제로 받은 것 | 결과 |
|---|---|---|
| `keystroke "o" using {command down}` | `chars=ㅐ mods=0x180028` = **⌘+⌥** | ⌥⌘O는 어느 항목과도 안 맞음 → **안 먹는 게 정상** |
| `key code 31 using {command down}` | `mods=0x100008` = ⌘만 | **정상 발화** |

**내 독립 확인**: 현재 선택된 입력 소스가 `com.apple.inputmethod.Korean.2SetKorean`이고, 2벌식에서 `o` 자리는 **ㅐ** — 프로브가 본 `chars=ㅐ`와 정확히 일치한다. 한글 IME가 활성일 때 System Events가 문자를 만들지 못해 **Option을 얹어 합성**하는 것이 원인이다.

**전수(키코드 기준)**: ⌘O·⌘P·⇧⌘F·⌥⌘1·⌥⌘0·⌃⌘V **전부 발화**. ⌃⌘R만 미발화이나 프로젝트 미개방이라 **비활성이 정상**.

### 방법 규율
**이 머신에서 `keystroke`로 단축키를 검증할 수 없다.** `key code`를 쓴다 — `O=31 P=35 F=3 1=18 0=29 V=9 R=15 W=13`.
정확한 진술은 "System Events가 안 먹는다"가 아니라 **"입력 소스에 따라 `keystroke`만 오염된다"**이다(frontend가 Finder ⌘N 포지티브 컨트롤로 하네스 자체는 정상임을 먼저 확인했다).

### 이 오류가 내 다른 결론도 뒤집는다
§3에서 **"SwiftUI `TextField`가 합성 입력에 포커스를 안 준다"**며 SC-3·6·9와 REQ-010 AC-1·2·5·6을 미검증으로 남겼는데, **그때도 같은 `keystroke`를 썼다.** 포커스 문제가 아니라 **IME가 입력을 먹은 것**일 가능성이 크다(NSOpenPanel ⇧⌘G 시트가 Return을 안 받은 것도 같은 원인일 수 있다). → **그 시나리오들은 자동화로 검증 가능할 수 있다.**

### 왜 내 관측으로는 알 수 없었나
나는 "눌렀는데 창 개수가 안 변한다"는 **바깥 관찰**만 했고, 그것은 *앱이 안 받았다*와 *앱이 다른 것을 받았다*를 구분하지 못한다. **프로브로 `mods` 비트를 읽은 순간** 답이 나왔다. 입력 계층을 의심할 때는 바깥에서 세지 말고 **안에서 읽어야** 한다.

### 16.2 Vim 모드의 ⌘Z — 설계상 비활성이 맞다. 다만 **부작용이 있다**
Vim 모드에서 ⌘Z는 **되돌리지 않았다.** 이는 설계대로다 — `MenuAvailability.swift:38`이 *"In Vim mode `u`, `y` and `p` already do that work"*라고 적고 Vim 모드에서 편집 명령을 비활성화한다(오늘 고친 REQ-010 AC-5 그 자체).
> ⚠️ 리더 지시는 "⌘Z가 모드 무관 경로로 바뀌었으니 두 모드 모두에서 확인하라"였는데, **실제 설계는 Vim 모드에서 비활성**이다. 지시와 구현이 어긋나 있으니 어느 쪽이 의도인지 확정이 필요하다.

**그런데 ⌘Z를 누른 뒤 에디터가 키 입력을 받지 못하게 됐다**:
```
① :e 로 파일 열기 → o + 텍스트 + Esc      ✅ 편집됨
② ⌃⌘V → 표준 → ⌘Z                        ✅ 되돌려짐
③ ⌃⌘V → Vim → o + 텍스트 + Esc            ✅ 편집됨 (여기까지 포커스 정상)
④ ⌘Z (Vim 모드)                            — 되돌리지 않음(설계대로)
⑤ u (Vim 되돌리기)                          🔴 되돌리지 않음
⑥ i                                        🔴 모드가 NORMAL 그대로 = 키가 안 감
```
→ **D-6 포커스 상실의 트리거가 모달만이 아니다.** ③까지 정상이던 포커스가 **④(비활성 메뉴 단축키)** 이후 사라졌다. 즉 **모달 닫기·비활성 단축키 등 앱 층이 개입하면 에디터가 first responder를 되찾지 못한다**는 더 일반적인 형태다.
