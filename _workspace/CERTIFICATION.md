도구였을 가능성이 크다.**

⚠ **`lsof` 로 판정하지 마라** — nvim 은 `--embed` 에서 stdin/stdout 을 내부 fd 로 dup 한 뒤
0·1 을 `/dev/null` 로 다시 연다(플러그인이 RPC 채널에 쓰는 것을 막으려고). **정상 세션과
고아가 `lsof` 상 구별되지 않는다.** backend-senior 가 이걸 보고 두 단계 잘못 갔다.
**정상과 결함이 같은 값을 내는 지표는 판정 도구가 아니다.**

→ **D-7 후보가 아니라 REQ-004 AC-1·REQ-NF-005 의 실증이다.**

### ✅ D-4 철회 — `keystroke` 가 한글 입력 소스에서 오염된다
프론트가 앱에 keyDown 프로브를 심어 실측:
```
keystroke "o" using {command down}  → 앱이 받은 것: chars=ㅐ mods=0x180028  = ⌘+⌥  ← 안 맞는 게 정상
key code 31   using {command down}  → mods=0x100008 (⌘만) → 발화, 패널 열림
```
**한글 입력 소스가 활성이면 System Events 의 `keystroke` 가 문자를 못 만들어 Option 을 얹어
합성한다.** 실제 사용자의 ⌘O 에는 Option 이 없다. **QA 와 리더의 재현 둘 다 하네스가 만든 가짜였다.**

**포지티브 컨트롤을 먼저 했다** — Finder ⌘N 으로 하네스 자체가 살아 있음을 확인한 뒤 결론을
냈다. 그래서 "System Events 가 죽었다"가 아니라 "한글 입력 소스에서 `keystroke` 가 오염된다"로
좁혀졌다.

**키코드 기준 전수 발화 확인**: ⌘O · ⌘P · ⇧⌘F · ⌥⌘1 · ⌥⌘0 · ⌃⌘V **전부 발화**.
⌃⌘R 만 미발화이고 **그건 정상**(프로젝트 미개방이라 비활성).

→ **규율: 자동화로 단축키를 잴 때는 `keystroke` 가 아니라 `key code` 를 쓴다.** 비라틴 입력
소스에서 `keystroke` 는 다른 수식키를 얹는다.

### 🔴 그 조사가 찾아낸 진짜 결함 둘 (수정 완료)

### 🔴 D-6 — 에디터에 타이핑이 안 된다 (리더 라이브 실측 18:4x)
**증거 (실측)**
```
AXFocusedUIElement → role=AXWindow          ← 창이 포커스다. 에디터 뷰가 아니다
편집기 클릭 후 i + "hello from leader"       → Neovim 상태줄 [No Name] 0,0-1 (버퍼 그대로)
```
**코드 근거**
- `EditorGridView:24` `acceptsFirstResponder = true` — 뷰는 받을 의사가 있다
- **`makeFirstResponder` 를 부르는 곳이 코드 전체에 0곳** — 아무도 포커스를 주지 않는다
- `EditorGridView.mouseDown` 은 이벤트를 Neovim 으로 전달만 하고 **포커스를 요청하지 않는다**

**AppKit 은 클릭만으로 평범한 `NSView` 를 first responder 로 만들지 않는다.** 텍스트 뷰가 스스로
그렇게 할 뿐이다. 그래서 `keyDown` 이 한 번도 불리지 않고, **REQ-010 AC-1("키 입력이 Neovim 에
전달된다")이 성립하지 않는다.**

### ✅ 수정 (프론트, 19:4x) — 합성 입력 아티팩트가 아니었다
```swift
override func mouseDown(with event: NSEvent) {
    window?.makeFirstResponder(self)   // 클릭하면 키보드를 요청한다
    forward(event, action: .press)
}

func takeFocusIfUnclaimed() {          // 등장 시 — 단, 아무도 안 잡았을 때만
    guard let window, window.firstResponder === window else { return }
    window.makeFirstResponder(self)
}
```
**조건부인 것이 핵심이다.** 무조건 잡으면 **SwiftUI 가 매 프레임 이 뷰를 갱신하므로 심볼 검색
필드에서 타이핑하는 중에 캐럿을 뺏어온다.** "창이 자기 자신의 first responder 인 상태 = 아무도
키보드를 안 잡았다"로 판정한다. 내가 지시한 "모달이 닫히면 에디터로 돌아오는가"를 그 조건이 덮는다.

**입력이 막혔을 때도 포커스는 잡는다** — *"Neovim 이 안 듣는다"와 "여기가 타이핑하는 곳이
아니다"는 다르다.* 세션이 돌아왔을 때 사용자가 칠 곳이 없어지면 안 된다.

⚠ **한 가지 유보**(수정 전 기록): 내 클릭은 합성 입력이었다. 다만 **이 메커니즘은 합성 여부와 무관**하다 —
포커스를 요청하는 코드가 아예 없다. 사람 손 클릭으로 1회 확인하면 확정된다.

**왜 지금까지 안 잡혔나**: 테스트는 `EditorGridView.keyDown(with:)` 을 **직접 호출**해 검증한다.
그건 "keyDown 이 불리면 올바로 동작하는가"이지 **"keyDown 이 불리기는 하는가"가 아니다.**
오늘 반복된 형태다 — 있는 테스트의 그린일 뿐이다.

### 지표는 둘이다 — 섞어 쓰면 안 된다
| 대상 | 세는 법 | 이유 |
|---|---|---|
| **뷰** | `\bName[({]` | 뷰는 `Name(...)` 로 생성된다(제네릭 뷰는 후행 클로저라 `{` 도) |
| **로직 모듈·정적 타입** | **맨이름** `\bName\b` (선언 파일 제외) | 이 코드베이스는 순수 로직을 `enum` 네임스페이스로 두는 관례라 **언제나 `Name.method(...)` 로만 불린다** |

**`Name(` 을 로직 모듈에 쓰면 가끔 틀리는 게 아니라 100% 틀린다.** 실측: 프론트 로직 모듈
10종 중 아홉이 `Name(` = 0 인데 **전부 실제로 소비 중**이다(`ShellSplitDrag`·`ShellVisibilityLayout`·
`WindowFrameFit`·`SpinnerDelay`·`IndexChipIndicator`·`IndexDetailsPresentation`·`RelativeTimeText`·
`PopoverPlacement`·`FileTreePresentation`). `PanelTint`·`CodeNavigatorApplication` 도 같은 이유다.

→ **같은 명령에 예외를 다는 것보다 검사를 둘로 나눈다.** 다음 사람이 헷갈리지 않는다.

그리고 반대 방향의 맹점이 더 위험하다: **검사 목록이 손으로 관리되면 새 뷰는 기본적으로
검사에서 빠진다.** 실제로 `IndexStatusChipView` · `SymbolSearchModalView` · `ShellSplitter`
셋이 미마운트인데 목록에 없어 게이트가 통과했다. 목록은 **기본 포함**이어야 한다 —
`View/` 의 뷰 타입을 전부 열거해 마운트를 요구하고, 의도적 예외만 명시적 허용목록에 둔다.
(그 때 `PanelTint` 같은 정적 전용 타입은 허용목록에 넣되 *이유를 적는다*.)

테스트가 아니다. 더블폭 문자·`startColumn`·커서 폭이 픽셀 수준 방어선을 갖는다(변이 실측 확인).
**화면 잠금과 무관하게 돈다.**
→ 그러므로 "렌더링을 재는 계기가 하나도 없다"는 틀렸다. **없는 것은 합성 층의 계기** —
어떤 뷰가 실제로 창에 꽂히는가. 마운트 카운트가 그 자리를 메운다.

## 2. 게이트 (리더가 직접 재실행 — 팀 주장이 아니라)

```bash
bash _workspace/gate.sh
```

포함: `swift build` · `swift test --no-parallel` · 실행 테스트 수 하한 · `.app` 조립 ·
번들 실행 검증 · 번들 검사기 자체 검사 · 민감정보 스캔.

**`--no-parallel` 인 이유**: 다섯 스위트가 각자 실제 Neovim 을 띄워, 병렬에서는 같은 코드가
부하에 따라 통과하기도 실패하기도 했다(5회 중 3회 실패 → 직렬 3회 전부 통과).

### ⚠ 자동화 안전 규칙 — 전역 좌표 클릭 금지
프론트의 합성 클릭이 **전역 좌표**를 썼는데 그 자리에 앱이 아니라 **리더의 터미널**이 있었다.
직후 보낸 키 셋이 남의 세션 입력란에 들어갔을 수 있다(Enter 는 안 보냄).
→ **합성 조작은 창 ID 기준으로만 한다.** 전역 좌표는 어느 앱을 때릴지 보장하지 않는다.
이 머신에는 사용자의 다른 작업이 함께 돌고 있다.

### ⚠ 인증 실행의 선행 조건 — 팀이 유휴여야 한다
**게이트에는 공유 자원을 잡거나 변형하는 스텝이 있다.** 팀원이 동시에 무언가를 돌리면
**제품과 무관한 거짓 실패**가 난다. 00:2x 실측 사례:
```
FAIL: verify-bundle --self-test   → 단독 재실행하면 4/4 통과 (공유 .app 을 rename 하는 스텝)
FAIL: 유휴 메모리 측정값 못 읽음   → swift test --filter 가 .build 락을 못 잡았다
```
**둘 다 실패한 게 옳다** — 못 쟀는데 통과시키지 않는 설계다. 다만 그 실패는 코드가 아니라
타이밍의 결과이므로, **인증 판정에 쓰려면 팀 유휴를 먼저 확인해야 한다.**

인증 절차:
1. `ListAgents` 로 팀 상태 확인 + 팀원에게 "게이트 돌린다, 잠시 멈춰라" 통지
2. 게이트 1회 실행
3. **실패가 나면 그 스텝만 단독 재실행**해서 경합인지 진짜인지 가른다
4. 경합이었으면 유휴를 다시 확인하고 게이트를 재실행해 **깨끗한 1회**를 얻는다

여기에 **뷰 조립 방어선**이 더해져야 한다(프론트 시니어 작업):
뷰 인스턴스화 테스트 + 조립 지점 고정. 단언 대상은 **"플레이스홀더가 아니다"** 여야 한다 —
"뷰가 만들어졌다"만 단언하면 플레이스홀더가 남아 있어도 통과한다.

### 표준 모드 메뉴 명령 — 실측된 결함 (수정 후 재검증 필수)
`MenuCommandRouter` 가 메뉴 명령을 **raw 키 문자열**로 보낸다. Vim 모드에선 맞지만 표준 모드에선
nvim 이 **삽입 모드**라 같은 키가 다른 뜻이 된다. backend-junior 가 실제 nvim 으로 재측정했다:

| 메뉴 | 보내는 것 | 표준 모드 실측 결과 |

**⌘S 가 가장 나쁘다 — "저장했다고 믿는데 저장되지 않는" 형태라 데이터 유실이다.**

엔진에는 **모드 안전한 경로가 이미 있다**(`EditorSession.jumpBack()` 은 `nvim_command` 로 실행해
모드와 무관하다 · `NeovimStandardMode.commandShortcuts` 는 `<D-z>`→`<C-o>u`, `<D-s>`→`<C-o>:write<CR>`
를 이미 갖고 있다). 만들어 놓고 안 연결한 것이다.

> **한글 자체가 그려졌는지는 한 번도 단언하지 않았다.**
> **"어디에 있나"와 "있기는 한가"는 다른 질문이다.**

### ✅ D-3 닫힘 — 그리고 이 건이 남긴 측정 교훈이 결함보다 값지다

**왜 세 번이나 판정이 뒤집혔는가 — 세 사람이 각각 틀린 방식이 다르다:**

| 누가 | 무엇을 쟀나 | 왜 못 잡았나 |
|---|---|---|
| 리더 | @1x 래스터를 **확대** | **확대는 없던 정보를 만들지 않는다** |

| 프론트 | **48pt** 렌더 | **결함이 크기 의존적이면 큰 크기는 반증이 못 된다** — advance 오차가 글리프 폭에 묻힌다 |

**옳은 지표는 잉크 덩어리 수**(연결 요소)였다:
```
        모노스페이스   시스템
⇧⌘F        1           3
⌥⌘0        1           3
ABC        2           3
```
→ **"겹쳤는가"를 세려면 폭이 아니라 틈을 센다.** 테스트도 덩어리 수로 바꿨고, **모노스페이스가
시스템 폰트보다 적은 덩어리를 낸다는 진단 자체를 테스트로 못 박았다** — 다음 사람이 키 표기에
`.monospaced` 를 다시 쓰려 하면 이유가 코드에 남아 있다.

**`ToolbarView.swift:107` 이 `design: .monospaced` 를 쓴다.** 수식키 기호(⇧⌘⌥⌃)가 모노스페이스
폰트에 없어 폴백되고, **폴백 글리프의 advance 가 셀 폭과 안 맞아 연속 2개 이상일 때 겹친다.**
QA 8배 확대: `⌘P` 정상 / `⇧⌘F` 겹침. **실제 영향은 3개 지점이다** — QA 가 처음 "문자열 7개"라 했으나
나머지 넷은 렌더 폰트가 `.system` 이라 애초에 안전했다(QA 자기 정정: *"문자열을 열거하고
렌더 경로를 확인하지 않은 채 영향으로 단정했다"*). 범위를 넓힌 방향은 옳았고 근거가 부실했다.

**프론트의 반증과 모순되지 않는다** — 프론트는 advance 6.80 정상, 잉크 폭 정비례를 쟀는데
**어느 폰트에서 쟀는지**가 갈린다. 모노스페이스에서 폴백된 경우를 안 쟀을 가능성이 크다.

**결정적 실험**(둘 중 하나로 끝난다): `⇧⌘F` 를 **regular 폰트와 monospaced 폰트 각각**에서
그려 ① 글리프가 그 폰트에 있는가 ② 잉크 폭이 글자 수에 비례하는가 를 **폰트별로** 비교한다.
같으면 겹침이 아니고, 모노스페이스에서만 어긋나면 D-3 은 실재하며 원인도 특정된다.

**내가 배운 것**: 나는 프론트의 반증을 받고 철회했는데, **그 반증이 문제의 조건(모노스페이스)
아래에서 이뤄졌는지 확인하지 않았다.** 반증도 재현 조건을 갖춰야 반증이다.

### 측정에서 걸린 거짓 그린 둘 (같은 실수를 반복하지 않기 위해)
1. **측정 대상이 이미 해제돼 있었다.** 첫 측정값이 "인덱스 비용 0.3MB" 였는데, 25,000 심볼이
   그럴 리 없다. 원인은 마지막 사용 이후 **ARC 가 엔진을 먼저 해제**한 것 — 사라진 인덱스를
   재고 "메모리를 거의 안 쓴다"고 통과하고 있었다. `withExtendedLifetime` 으로 감싸니 20.1MB.
2. **같은 프로세스에서는 증가분이 0 으로 나온다.** 앞선 테스트가 잡아둔 페이지를 재사용하기
   때문이다(단독 20.1MB / 전체 스위트 안에서 0.0MB). 그래서 SC-8 은 게이트에서 **격리 실행**해
   출력 숫자로 판정한다.

→ 그리고 숫자를 믿기 전에 **측정기 자체를 검사**했다(50MB 를 실제로 할당·터치 → 관측 증가
50.0MB). **측정기가 죽어 있으면 150MB 예산 테스트는 무엇을 재든 영원히 통과한다.**

## 6. 증거로 인정하지 않는 것

- **"파일이 존재한다"** — 라우트 파일이 있고 등록도 됐는데 엔드포인트가 TODO 였던 사례가 있다.
- **"테스트가 전부 초록"** — 존재하는 테스트의 그린일 뿐이다. 뷰 테스트 0건인 상태에서도 630건이 초록이었다.
- **매트릭스의 `테스트 상태` PASS** — "나열된 테스트가 통과한다"는 뜻이지 화면 성립이 아니다.
- **`--self-check` 통과** — `CodeNavigatorMain.swift` 에서 `run()` **이전에 return** 한다. 창·뷰 생성을 실행하지 않는다.
- **팀의 자가 라이브 E2E·디자인 충실도 PASS** — 이 둘은 리더 인증 단계다. 팀이 돌렸으면 "팀 자가검증(리더 인증 대기)"로만 표기한다.
- **생산 쪽 참조만 세는 것** — 값을 *쓰는* 호출부가 있으면 grep 은 "쓰이고 있음"으로 읽는다.
  실측: `MenuCommandRouter` 가 `setTreeVisible`/`setPanelVisible` 을 부르고 `ShellPreferences` 가
  저장·복원까지 하는데 **그 값을 읽는 쪽이 없어** 메뉴는 반응하고 화면은 안 바뀌었다.
  미구현보다 이 상태가 덜 보인다 — 호출부가 있으니 연결된 것처럼 읽힌다.
  **소비처까지 세어야 연결 확인이다.**
- **이미 성립한 상태를 그 조작의 결과로 읽는 것** — 실측: 클릭이 포커스를 가져오는지 보는 테스트가
  `mouseDown` 의 포커스 요청을 **빼도 그린**이었다. `viewDidMoveToWindow` 가 이미 포커스를 준
  뒤라 **"클릭이 가져왔다"가 아니라 "원래 갖고 있었다"를 보고 있었다.**
  → **조작의 효과를 재려면 그 조작 전에 반대 상태를 만들어야 한다**(키보드를 다른 필드에 맡겨
  놓고 클릭). 마침 그게 실제 사용자 동선이기도 하다 — 검색어 치다가 코드로 돌아오는 것.
- **명세를 읽고 재구성한 값으로 재는 것** — 실측: 시각 회귀 게이트가 수식키를 `.monospaced` 로
  그려 쟀다(§4.2 의 "kbd 11px 모노" 를 그대로 읽어서). **그런데 실제 툴바는 `.shortcutLabel()`
  = `.system` 이다** — 시니어가 D-3 을 고치며 폰트를 바꿨기 때문이다.
  → **고쳐진 결함의 옛 렌더를 재고 "현재 상태"로 보고**했고, 리더는 그 위에서 "허용, 하한 2" 를
  판정했다. **그대로 갔으면 게이트가 자기가 잡으라고 만들어진 결함을 합격시켰을 것이다.**
  → **뷰가 실제로 쓰는 값은 뷰에서 읽어라.** 명세와 구현이 갈린 자리에서 조용히 어긋난다.
  → 리더 몫: **나는 "2 덩어리"를 받고 "어느 폰트에서 쟀나"를 묻지 않았다.** D-3 철회 때와
  **같은 실수를 두 번째로 했다** — 남의 측정을 받을 때 그 측정의 조건을 확인하지 않는 것.
- **준비 확인이 본 단언과 다른 동작을 하는 것** — 리더가 만든 마우스 워밍업이 `(5,0)→(6,3)`
  으로 드래그했는데 **그 좌표는 선택을 만들지 않는다**(`(0,0)→(2,5)` 는 만든다). 그래서 준비
  확인이 60회를 전부 태우고 리셋에도 도달하지 못한 채 본 단언으로 넘어갔다.
  → **워밍업이 단언과 다른 일을 하면 "준비됨" 판정 자체가 거짓이 된다.** 준비 조건은 본
  단언이 의존하는 능력을 *같은 방식으로* 확인해야 한다.
- **걸러낸 목록을 도는 테스트** — `for x in allKnownCases where <조건>` 은 **조건에 걸리는 게
  하나도 없으면 한 번도 안 돌고 초록으로 통과한다.** `--filter` 0매치 초록불과 같은 형태다.
  걸러낸 결과를 먼저 변수로 받고 `#expect(!filtered.isEmpty)` 를 앞에 세워야 한다.
  → 완전성 목록을 `allKnownCases` 로 바꾸는 것만으로는 부족하고, 오히려 **더 조용한 통과
  경로**를 만들 수 있다.
- **한 번 통과한 실행만 보고 그린이라 부르는 것** — 실측: 드래그 테스트가 고립 실행 4회 중
  3회 실패였는데(실패는 5.5초 타임아웃, 성공은 0.5초) 통과한 실행만 보고 "5/5 그린"으로
  보고됐다. **비결정적 테스트는 반복 실행으로만 드러난다.** 오늘 재현 안 되던 게이트 실패
  둘이 전부 이 계열이었다.
- **단위 테스트 통과를 요구사항 충족으로 읽는 것** — 모듈은 *자기가 약속한 것*을 지키고,
  요구사항이 약속한 것은 **조합해 봐야** 드러난다. 실측: `PopoverPlacement` 는 "어느 쪽에도
  자리가 없으면 영역 안에 가둔다"를 지켰고 그 테스트도 통과했는데, 낮은 창에서 그 결과가
  **커서 줄을 덮었다**(카드 `(80,8,460×308)` 가 앵커 `(80,90,8×18)` 를 가림). 02 §3 W-4 의
  "팝오버가 커서 줄을 절대 덮지 않는다"가 깨지는데 단위 테스트는 초록이었다.
  → **모듈의 계약과 요구사항의 계약은 다른 문서다.** 배선한 뒤 산술을 따라가야 드러난다.
- **테스트 참조를 소비로 세는 것** — 이게 "존재≠완료"의 **가장 조용한 형태**다. 실측:
  `PopoverPlacement` 는 참조 11건이라 쓰이는 것처럼 보였는데 **전부 테스트였고 소스 참조는 0**이었다.
  그래서 팝오버 플립·"커서 줄을 덮지 않는다"가 구현돼 있지 않은데 모듈은 완전히 테스트돼 있다.
  **모듈은 완전히 테스트되면서 동시에 완전히 고아일 수 있고, 테스트가 그 사실을 가린다.**
  커버리지 매트릭스가 PASS 로 가득한데 화면에 그 기능이 없는 상황이 정확히 이렇게 만들어진다.
  → 세는 범위를 **`Sources/` 와 `Tests/` 로 나눠서** 봐라.
- **이름이 완전성을 주장하는 테스트** — `ShellCompositionTests` 의 "만들어 놓고 안 쓰는 것이 없다"가
  통과하는 동안 `ShellSplitter` 는 참조 0이었다. 그 테스트는 `ShellPane.allCases` 만 훑는데,
  스플리터는 "영역"이 아니라 목록에 없었다. **이름이 완전성을 주장하면 다음 사람은 그 뒤를 안 본다.**
- **연쇄 실패를 원인 여럿으로 읽는 것** — 빌드나 테스트 컴파일이 깨지면 뒤따르는 스텝이 전부
  빨간불이 된다(테스트 수 판독 실패 · 유휴 메모리 판독 실패 · `.app` 조립 실패 …).
  **출력만 보면 원인이 여럿 같지만 뿌리는 하나다.**
- **낡은 실측을 현재 상태로 반복하는 것** — "아직 안 꽂혔다"는 **상태 주장이지 사실이 아니다.**
  시간이 지나면 저절로 틀려진다. 실측: 23:33 의 "미배선 0건"이 정확했는데(배선은 23:36 에
  들어왔다) 그 값이 00:08 보고까지 **35분 동안 재측정 없이 현재형으로 반복**됐다.
  → **상태 주장을 반복하기 전에 다시 잰다.** 통지에 검증 시각을 병기하는 이유가 이것이다.
- **경로를 철자로 비교하는 것** — **경로의 철자와 경로가 가리키는 곳은 다르다.** 이 빌드에서
  **세 번** 나왔다: ① 트리 강조(`/tmp`↔`/private/tmp`) ② 탭 정체성(AC-5, 같은 프로젝트에 탭 둘)
  ③ **샌드박스 루트 탈출**(보안 경계라 가장 비싸다).
  → **경로 비교는 항상 해석 후에 한다** — 심링크 해석 · `..` 붕괴 · **구분자까지 포함한 접두 비교**
  (`/repo-secrets` 는 `/repo` 안이 아니다).
- **빈 명령 출력** — 그 명령이 잡을 수 있는지부터 확인한다. 리더가 `ioreg` 빈 결과를 "잠금 해제"로 오독했고,
  스크린샷 파일 크기를 "찍힘"의 증거로 삼았다(내용은 배경화면이었다). 미마운트를 세는 임시
  스크립트가 셸 문법 오류로 매 루프 실패하면서 "22종 전부 미마운트"라는 그럴듯한 경보를 내기도
  했다. **두 측정이 반대를 가리키면 먼저 측정기를 의심한다.**
