**"테스트 그린"과 "사용자가 할 수 있다"를 한 칸에 섞으면 인증이 흐려진다.** 그래서 판정을 나눈다:

### ⚠ D-2 재개봉 (QA 19:00 실측) — 이전 강등은 표본이 한쪽이었다
```
83810     1  18:56:01  nvim --embed   ← PPID=1 고아 (18:56 D-7 실패 인스턴스가 남긴 것)
91349  90842 18:58:13  nvim --embed   ← 현재 앱의 정상 자식
```
**이전 "고아 0" 3회는 전부 세션이 성공한 경우였다.** 정확한 진술:

| 경로 | 고아 |
|---|---|
| 정상 종료(세션 성공) | **0** ✅ |
| SIGKILL(세션 성공) | **0** ✅ (nvim 이 파이프 EOF 로 자멸) |
| **D-7 실패 세션** | **발생** 🔴 |

→ **D-2 와 D-7 은 별개가 아니라 하나의 사슬이다.** 그리고 **`다시 확인` 재시도가 이전 것을
회수하지 않아 누적된다** — 이건 `start()` 정리 수정과 별개의 경로다.

### (참고) 이전 강등 근거 — 성공 경로에 한해서는 여전히 유효하다
| 경로 | 결과 |
|---|---|
| 프로젝트 열기 | nvim `PPID=앱` — 정상 부모 |
| **정상 종료** | **고아 0** ✅ |
| **SIGKILL** | **고아 0** ✅ |

**SIGKILL 에서도 깨끗한 이유**: nvim 은 **RPC 파이프가 닫히면 스스로 종료**한다. 종료 훅이
안 불려도 EOF 가 정리를 보장한다 — 설계가 원래 견고했다. backend-senior 단일 프로세스
실측도 일치한다(`kill -9` 후 자식이 stdin EOF 로 자멸).

**고아는 "세션 여럿이 떠 있는 상태에서 부모가 급사"할 때 난다**(3개 띄우고 `kill -9` → 1~2개
고아). **그건 정확히 `pkill` 버그가 만들던 상황이다** — 스크린샷 스크립트가 테스트 번들을
죽여 앱이 세션 중간에 급사했다. **17:52 의 고아는 실재했으나 원인이 제품이 아니라 우리
도구였을 가능성이 크다.**

⚠ **`lsof` 로 판정하지 마라** — nvim 은 `--embed` 에서 stdin/stdout 을 내부 fd 로 dup 한 뒤
0·1 을 `/dev/null` 로 다시 연다(플러그인이 RPC 채널에 쓰는 것을 막으려고). **정상 세션과
고아가 `lsof` 상 구별되지 않는다.** backend-senior 가 이걸 보고 두 단계 잘못 갔다.
**정상과 결함이 같은 값을 내는 지표는 판정 도구가 아니다.**

**남은 가설**(재현 못 함): `nvim_ui_attach` 를 끝내지 못한 세션은 파이프 상태가 달라 부모
사망을 감지하지 못할 수 있다. REQ-012 는 이 위험을 **줄인다** — 탭페이지 모델이라 프로젝트가
넷이어도 nvim 은 하나다.

**AppKit 은 클릭만으로 평범한 `NSView` 를 first responder 로 만들지 않는다.** 텍스트 뷰가 스스로
그렇게 할 뿐이다. 그래서 `keyDown` 이 한 번도 불리지 않고, **REQ-010 AC-1("키 입력이 Neovim 에
전달된다")이 성립하지 않는다.**

### ✅ 수정 (프론트, 19:4x) — 합성 입력 아티팩트가 아니었다
```swift
override func mouseDown(with event: NSEvent) {
    window?.makeFirstResponder(self)   // 클릭하면 키보드를 요청한다
    forward(event, action: .press)
}

func takeFocusIfUnclaimed() {          // 등장 시 — 단, 아무도 안 잡았을 때만
    guard let window, window.firstResponder === window else { return }
    window.makeFirstResponder(self)
}
```
**조건부인 것이 핵심이다.** 무조건 잡으면 **SwiftUI 가 매 프레임 이 뷰를 갱신하므로 심볼 검색
필드에서 타이핑하는 중에 캐럿을 뺏어온다.** "창이 자기 자신의 first responder 인 상태 = 아무도
키보드를 안 잡았다"로 판정한다. 내가 지시한 "모달이 닫히면 에디터로 돌아오는가"를 그 조건이 덮는다.

**입력이 막혔을 때도 포커스는 잡는다** — *"Neovim 이 안 듣는다"와 "여기가 타이핑하는 곳이
아니다"는 다르다.* 세션이 돌아왔을 때 사용자가 칠 곳이 없어지면 안 된다.

⚠ **한 가지 유보**(수정 전 기록): 내 클릭은 합성 입력이었다. 다만 **이 메커니즘은 합성 여부와 무관**하다 —
포커스를 요청하는 코드가 아예 없다. 사람 손 클릭으로 1회 확인하면 확정된다.

**왜 지금까지 안 잡혔나**: 테스트는 `EditorGridView.keyDown(with:)` 을 **직접 호출**해 검증한다.
그건 "keyDown 이 불리면 올바로 동작하는가"이지 **"keyDown 이 불리기는 하는가"가 아니다.**
오늘 반복된 형태다 — 있는 테스트의 그린일 뿐이다.

### 지표는 둘이다 — 섞어 쓰면 안 된다
| 대상 | 세는 법 | 이유 |
|---|---|---|
| **뷰** | `\bName[({]` | 뷰는 `Name(...)` 로 생성된다(제네릭 뷰는 후행 클로저라 `{` 도) |
| **로직 모듈·정적 타입** | **맨이름** `\bName\b` (선언 파일 제외) | 이 코드베이스는 순수 로직을 `enum` 네임스페이스로 두는 관례라 **언제나 `Name.method(...)` 로만 불린다** |

**`Name(` 을 로직 모듈에 쓰면 가끔 틀리는 게 아니라 100% 틀린다.** 실측: 프론트 로직 모듈
10종 중 아홉이 `Name(` = 0 인데 **전부 실제로 소비 중**이다(`ShellSplitDrag`·`ShellVisibilityLayout`·
`WindowFrameFit`·`SpinnerDelay`·`IndexChipIndicator`·`IndexDetailsPresentation`·`RelativeTimeText`·
`PopoverPlacement`·`FileTreePresentation`). `PanelTint`·`CodeNavigatorApplication` 도 같은 이유다.

→ **같은 명령에 예외를 다는 것보다 검사를 둘로 나눈다.** 다음 사람이 헷갈리지 않는다.

그리고 반대 방향의 맹점이 더 위험하다: **검사 목록이 손으로 관리되면 새 뷰는 기본적으로
검사에서 빠진다.** 실제로 `IndexStatusChipView` · `SymbolSearchModalView` · `ShellSplitter`
셋이 미마운트인데 목록에 없어 게이트가 통과했다. 목록은 **기본 포함**이어야 한다 —
`View/` 의 뷰 타입을 전부 열거해 마운트를 요구하고, 의도적 예외만 명시적 허용목록에 둔다.
(그 때 `PanelTint` 같은 정적 전용 타입은 허용목록에 넣되 *이유를 적는다*.)

→ 그러므로 "렌더링을 재는 계기가 하나도 없다"는 틀렸다. **없는 것은 합성 층의 계기** —

### ⚠ 자동화 안전 규칙 — 패턴으로 프로세스를 죽이지 않는다 (오늘 2회)
| 시각 | 누가 | 패턴 | 잡힌 것 |
|---|---|---|---|
| 17:5x | frontend-senior | `pkill -f "CodeNavigator"` | **`CodeNavigatorPackageTests`** — 남의 테스트 실행이 매번 죽었다 |

**두 번째는 첫 번째 교훈을 읽은 뒤에 났다.** 즉 "조심하자"로는 안 막힌다.
→ **규율: 공유 머신에서는 자기가 띄운 PID 만 지정해 죽인다.** 패턴 매칭으로 정리하지 않는다.
이 머신에는 팀원 여럿과 **사용자의 다른 작업**이 함께 돌고 있다.

### ⚠ 자동화 안전 규칙 — 전역 좌표 클릭 금지
프론트의 합성 클릭이 **전역 좌표**를 썼는데 그 자리에 앱이 아니라 **리더의 터미널**이 있었다.

→ **합성 조작은 창 ID 기준으로만 한다.** 전역 좌표는 어느 앱을 때릴지 보장하지 않는다.
이 머신에는 사용자의 다른 작업이 함께 돌고 있다.

### ⚠ 인증 실행의 선행 조건 — 팀이 유휴여야 한다
**게이트에는 공유 자원을 잡거나 변형하는 스텝이 있다.** 팀원이 동시에 무언가를 돌리면
**제품과 무관한 거짓 실패**가 난다. 00:2x 실측 사례:
```
FAIL: verify-bundle --self-test   → 단독 재실행하면 4/4 통과 (공유 .app 을 rename 하는 스텝)
FAIL: 유휴 메모리 측정값 못 읽음   → swift test --filter 가 .build 락을 못 잡았다
```
**둘 다 실패한 게 옳다** — 못 쟀는데 통과시키지 않는 설계다. 다만 그 실패는 코드가 아니라
타이밍의 결과이므로, **인증 판정에 쓰려면 팀 유휴를 먼저 확인해야 한다.**

인증 절차:
1. `ListAgents` 로 팀 상태 확인 + 팀원에게 "게이트 돌린다, 잠시 멈춰라" 통지
2. 게이트 1회 실행
3. **실패가 나면 그 스텝만 단독 재실행**해서 경합인지 진짜인지 가른다
4. 경합이었으면 유휴를 다시 확인하고 게이트를 재실행해 **깨끗한 1회**를 얻는다

여기에 **뷰 조립 방어선**이 더해져야 한다(프론트 시니어 작업):

### ~~D-3 철회~~ (철회를 철회함 — 위 참조)
내가 "수식키가 둘 이상이면 겹쳐 그려진다"고 확정했으나 **틀렸다.**

| 실측 | 결과 |
|---|---|
| 폰트 글리프·advance | `⌘`·`⇧`·`⌥`·`⌃` 전부 **glyph 존재, advance 6.80 정상** (한글은 `glyph=0` 이었다 — 다른 종류다) |
| 그려진 잉크 폭 | `⌘P`=13px · `⇧⌘F`=20px · `⌥⌘0`=20px. **같은 글자 수의 평범한 문자열과 정확히 같다.** 겹쳤다면 수식키를 더해도 폭이 안 늘어난다 |
| 48pt 렌더 | 넷 다 기호가 **또렷이 분리**돼 있다 |

**진짜 원인**: 이 디스플레이가 **`backingScaleFactor = 1.0`**(비-Retina)이다. 11pt 수식키는 ~11px
안에 획이 여럿인 조밀한 글리프라 @1x 에서 뭉개진다.

**내 방법론 오류**: 나는 @1x 래스터를 **확대**해 놓고 그것을 "해상도를 올려 확정했다"고 적었다.
**확대는 없던 정보를 만들지 않는다.** 확대(magnification)와 해상도(resolution)는 다르고,
내 인증 기준에 "해상도를 올리는 것이 맞았다"고 쓴 문장 자체가 그 둘을 섞고 있었다.

⚠ **앱에 프로젝트를 비대화식으로 여는 경로가 없다**(argv 핸들러·`application(_:open:)`·자동 복원

### 측정에서 걸린 거짓 그린 둘 (같은 실수를 반복하지 않기 위해)
1. **측정 대상이 이미 해제돼 있었다.** 첫 측정값이 "인덱스 비용 0.3MB" 였는데, 25,000 심볼이
   그럴 리 없다. 원인은 마지막 사용 이후 **ARC 가 엔진을 먼저 해제**한 것 — 사라진 인덱스를
   재고 "메모리를 거의 안 쓴다"고 통과하고 있었다. `withExtendedLifetime` 으로 감싸니 20.1MB.
2. **같은 프로세스에서는 증가분이 0 으로 나온다.** 앞선 테스트가 잡아둔 페이지를 재사용하기
   때문이다(단독 20.1MB / 전체 스위트 안에서 0.0MB). 그래서 SC-8 은 게이트에서 **격리 실행**해
   출력 숫자로 판정한다.

→ 그리고 숫자를 믿기 전에 **측정기 자체를 검사**했다(50MB 를 실제로 할당·터치 → 관측 증가
50.0MB). **측정기가 죽어 있으면 150MB 예산 테스트는 무엇을 재든 영원히 통과한다.**

### ⚖️ 인증 기준 갱신 (2026-08-30 21:4x, 리더)

**리더 인증은 풀게이트 1회 그린으로 하지 않는다. 연속 3회 그린을 요구한다.**

근거: backend-senior 가 풀런 **13회**를 돌려 **그린 ~60%** 를 실측했다. 그 13회가 없었으면
**나는 운 좋은 1회로 인증했을 것이다.** §6 의 *"한 번 통과한 실행만 보고 그린이라 부르는 것"* 이
인증 절차 자체에 적용된 경우다 — 우리는 그 함정을 남의 테스트에서만 보고 있었다.

**60% 게이트에서 1회 그린을 뽑는 것은 동전 던지기다.** 그리고 그 동전은
"코드가 옳은가"가 아니라 "이번에 운이 좋았나"를 답한다.

## 6. 증거로 인정하지 않는 것

- **"파일이 존재한다"** — 라우트 파일이 있고 등록도 됐는데 엔드포인트가 TODO 였던 사례가 있다.
- **"테스트가 전부 초록"** — 존재하는 테스트의 그린일 뿐이다. 뷰 테스트 0건인 상태에서도 630건이 초록이었다.
- **매트릭스의 `테스트 상태` PASS** — "나열된 테스트가 통과한다"는 뜻이지 화면 성립이 아니다.
- **`--self-check` 통과** — `CodeNavigatorMain.swift` 에서 `run()` **이전에 return** 한다. 창·뷰 생성을 실행하지 않는다.
- **팀의 자가 라이브 E2E·디자인 충실도 PASS** — 이 둘은 리더 인증 단계다. 팀이 돌렸으면 "팀 자가검증(리더 인증 대기)"로만 표기한다.
- **생산 쪽 참조만 세는 것** — 값을 *쓰는* 호출부가 있으면 grep 은 "쓰이고 있음"으로 읽는다.
  실측: `MenuCommandRouter` 가 `setTreeVisible`/`setPanelVisible` 을 부르고 `ShellPreferences` 가
  저장·복원까지 하는데 **그 값을 읽는 쪽이 없어** 메뉴는 반응하고 화면은 안 바뀌었다.
  미구현보다 이 상태가 덜 보인다 — 호출부가 있으니 연결된 것처럼 읽힌다.
  **소비처까지 세어야 연결 확인이다.**
- **이미 성립한 상태를 그 조작의 결과로 읽는 것** — 실측: 클릭이 포커스를 가져오는지 보는 테스트가
  `mouseDown` 의 포커스 요청을 **빼도 그린**이었다. `viewDidMoveToWindow` 가 이미 포커스를 준
  뒤라 **"클릭이 가져왔다"가 아니라 "원래 갖고 있었다"를 보고 있었다.**
  → **조작의 효과를 재려면 그 조작 전에 반대 상태를 만들어야 한다**(키보드를 다른 필드에 맡겨
  놓고 클릭). 마침 그게 실제 사용자 동선이기도 하다 — 검색어 치다가 코드로 돌아오는 것.
- **정리 코드가 불리는지 확인하지 않는 것** — 실측(D-2 근본 원인): 채널의 리더 태스크가
  `self` 를 **강하게 캡처**해 사슬이 닫혀 있었다. *태스크는 스트림이 열려 있는 한 돌고 · 스트림은
  프로세스가 사는 한 열려 있고 · 프로세스는 채널이 해제되지 않아 계속 산다.*
  → **세션을 버리면 아무도 닿을 수 없는 편집기가 남고 `deinit` 조차 불리지 않는다.**
  백엔드가 `deinit` 정리를 넣었는데 **안 불려서** 그때 원인을 알았다 — **그 실패가 원인을 가리켰다.**
  → `weak self` 는 위생이 아니라 **자원 회수의 핵심**일 수 있다. 그리고 **정리를 넣었으면 그것이
  실제로 불리는지부터 재라.**
- **판정 근거를 계약에 남기지 않는 것** — 남기지 않으면 **소비자는 있는 필드로 추측한다.**
  실측: `EditorStartupFailure` 에 **종류가 없어** 부재를 판정할 단서가 `foundVersion == nil`
  뿐이었고, **타임아웃도 버전이 nil 이라 같은 문구**("Neovim 없음")가 나왔다. 프론트는 계약이
  말한 대로 정확히 그렸다 — **문구 결함처럼 보였지만 뿌리는 계약이었다.**
  → 그리고 **그 종류에 기본값을 주지 않은 것**이 맞다. `filesSearched` 같은 정보성 필드는
  기본값이 옳지만, **판정은 기본값이 있으면 실제 코드 경로가 조용히 틀린 종류를 주장한다.**
- **명세를 읽고 재구성한 값으로 재는 것** — 실측: 시각 회귀 게이트가 수식키를 `.monospaced` 로
  그려 쟀다(§4.2 의 "kbd 11px 모노" 를 그대로 읽어서). **그런데 실제 툴바는 `.shortcutLabel()`
  = `.system` 이다** — 시니어가 D-3 을 고치며 폰트를 바꿨기 때문이다.
  → **고쳐진 결함의 옛 렌더를 재고 "현재 상태"로 보고**했고, 리더는 그 위에서 "허용, 하한 2" 를
  판정했다. **그대로 갔으면 게이트가 자기가 잡으라고 만들어진 결함을 합격시켰을 것이다.**
  → **뷰가 실제로 쓰는 값은 뷰에서 읽어라.** 명세와 구현이 갈린 자리에서 조용히 어긋난다.
  → 리더 몫: **나는 "2 덩어리"를 받고 "어느 폰트에서 쟀나"를 묻지 않았다.** D-3 철회 때와
  **같은 실수를 두 번째로 했다** — 남의 측정을 받을 때 그 측정의 조건을 확인하지 않는 것.
- **준비 확인이 본 단언과 다른 동작을 하는 것** — 리더가 만든 마우스 워밍업이 `(5,0)→(6,3)`
  으로 드래그했는데 **그 좌표는 선택을 만들지 않는다**(`(0,0)→(2,5)` 는 만든다). 그래서 준비
  확인이 60회를 전부 태우고 리셋에도 도달하지 못한 채 본 단언으로 넘어갔다.
  → **워밍업이 단언과 다른 일을 하면 "준비됨" 판정 자체가 거짓이 된다.** 준비 조건은 본
  단언이 의존하는 능력을 *같은 방식으로* 확인해야 한다.
- **걸러낸 목록을 도는 테스트** — `for x in allKnownCases where <조건>` 은 **조건에 걸리는 게
  하나도 없으면 한 번도 안 돌고 초록으로 통과한다.** `--filter` 0매치 초록불과 같은 형태다.
  걸러낸 결과를 먼저 변수로 받고 `#expect(!filtered.isEmpty)` 를 앞에 세워야 한다.
  → 완전성 목록을 `allKnownCases` 로 바꾸는 것만으로는 부족하고, 오히려 **더 조용한 통과
  경로**를 만들 수 있다.
- **한 번 재고 원인을 확정하는 것 — 답이 "때에 따라 다르다"일 때** — 실측(D-13, frontend-senior):
  같은 로직·같은 시퀀스를 **한 앱 인스턴스에서 두 번** 돌렸더니 결과가 갈렸다.
  ```
  1차(기동 직후):  ㅎ → insertText 'ㅎ'   (IME 가 마킹 없이 즉시 커밋) → 최종 `ㅎㅏ`
  2차(곧바로):     ㅎ → setMarkedText 'ㅎ' → '하' 조합            → 최종 `하`  ✅
  ```
  **`ㅎㅏ` 는 우리 코드가 만든 게 아니라 IME 의 첫 타건 동작이었다.** 입력 컨텍스트 활성화
  직후에만 조합을 건너뛴다.
  → **리더 가설(`discardMarkedText()` 가 버린다)도 시니어 가설(`setMarkedText` 가 조합본을
  안 준다)도 둘 다 틀렸다.** 정답은 **둘 중 하나가 아니라 "때에 따라"** 였다.
  → **한 번만 쟀으면 멀쩡한 커밋 경로를 뜯어고쳤을 것이다.** 그리고 그 수정은 2차부터는
  옳게 돌던 코드를 망가뜨렸을 것이다 — **결함을 못 고치는 것보다 나쁜 결과다.**
  → 그리고 **QA 의 원래 측정도 틀리지 않았다.** `ㅎㅏ` 는 실제로 일어난 일이고, **한 번만
  쟀다는 것이 유일한 한계**였다. **틀린 관측과 불완전한 관측은 다르다.**
  → 짝이 되는 규율: §6 의 *"한 번 통과한 실행만 보고 그린이라 부르지 마라"* 의 **원인 규명판**.
  통과만이 아니라 **실패도 한 번으로 확정하면 안 된다.**
- **한 번 통과한 실행만 보고 그린이라 부르는 것** — 실측: 드래그 테스트가 고립 실행 4회 중
  3회 실패였는데(실패는 5.5초 타임아웃, 성공은 0.5초) 통과한 실행만 보고 "5/5 그린"으로
  보고됐다. **비결정적 테스트는 반복 실행으로만 드러난다.** 오늘 재현 안 되던 게이트 실패
  둘이 전부 이 계열이었다.
- **단위 테스트 통과를 요구사항 충족으로 읽는 것** — 모듈은 *자기가 약속한 것*을 지키고,
  요구사항이 약속한 것은 **조합해 봐야** 드러난다. 실측: `PopoverPlacement` 는 "어느 쪽에도
  자리가 없으면 영역 안에 가둔다"를 지켰고 그 테스트도 통과했는데, 낮은 창에서 그 결과가
  **커서 줄을 덮었다**(카드 `(80,8,460×308)` 가 앵커 `(80,90,8×18)` 를 가림). 02 §3 W-4 의
  "팝오버가 커서 줄을 절대 덮지 않는다"가 깨지는데 단위 테스트는 초록이었다.
  → **모듈의 계약과 요구사항의 계약은 다른 문서다.** 배선한 뒤 산술을 따라가야 드러난다.
- **테스트 참조를 소비로 세는 것** — 이게 "존재≠완료"의 **가장 조용한 형태**다. 실측:
  `PopoverPlacement` 는 참조 11건이라 쓰이는 것처럼 보였는데 **전부 테스트였고 소스 참조는 0**이었다.
  그래서 팝오버 플립·"커서 줄을 덮지 않는다"가 구현돼 있지 않은데 모듈은 완전히 테스트돼 있다.
  **모듈은 완전히 테스트되면서 동시에 완전히 고아일 수 있고, 테스트가 그 사실을 가린다.**
  커버리지 매트릭스가 PASS 로 가득한데 화면에 그 기능이 없는 상황이 정확히 이렇게 만들어진다.
  → 세는 범위를 **`Sources/` 와 `Tests/` 로 나눠서** 봐라.
- **한계를 재지 않고 한계라고 적는 것** — 실측(frontend-junior): 스캐너의 알려진 한계를
  테스트로 문서화하라고 지시했더니, **적기 전에 재 보고 자기 주석의 절반이 거짓임을 찾았다.**
  ```
  주석: "주석·CDATA·따옴표 없는 속성을 모른다"
  실측: 주석 ✅잡는다   CDATA ✅잡는다   따옴표 없는 값 ❌   속성값 안의 `>` ❌(몰랐음)   `=` 주변 공백 ❌(몰랐음)
  ```
  **절반은 거짓이었고, 진짜 구멍 둘은 아예 몰랐다.**
  → 가장 고약한 것: `<img alt="a>b" src="https://evil.com/w.png">` 에서 **첫 `>` 를 태그 끝으로 봐
  요소가 잘리고, 뒤의 진짜 `src` 는 검사조차 안 됐다.** 차단 목록에도 안 실린다 —
  **사용자에게 "아무것도 차단 안 됨"으로 보인다.**
  → **셋 다 "비용 대비 안 막는 한계"가 아니라 그냥 우회였다.** 따옴표만 빼면 1층이 통째로 뚫린다.
  → **문서화 지시가 결함을 찾아냈다.** 한계를 *실행 가능한 형태*로 만들라고 하면 **먼저 재게 되고,
  그때 한계 목록이 틀렸음이 드러난다.** 주석은 재지 않고도 쓸 수 있지만 테스트는 그럴 수 없다.
  → **적기 전에 재 보지 않았으면 거짓을 테스트로 굳혔을 것이다** — 주석의 거짓보다 나쁘다.
- **두 층 중 한 층만 재고 "이중 방어"라 부르는 것** — 실측(frontend-junior 자진 보고):
  렌더 보안은 ①전처리 재작성 ②CSP 백스톱의 2겹인데, **①만 실측됐다.** CSP 는
  *"메타 태그를 문서에 넣었다"* 까지가 보장이고 **WebKit 이 우리 로드 방식에서 그 정책을 실제로
  강제하는지는 측정된 적이 없다.**
  → 콘텐츠 룰(ADR-0109)은 시니어가 실제 리스너로 쟀는데 **CSP 는 그 대접을 못 받았다.**
  → **이것이 1층을 느슨하게 두면 안 되는 진짜 이유다** — 두 층 중 **확인된 것은 1층뿐**이므로,
  지금 우리가 가진 것은 "이중"이 아니라 **"확인된 하나 + 가정된 하나"** 다.
  → 일반형: **겹을 세기 전에 각 겹이 실제로 막는지 재라.** 안 재면 겹의 수는 안심의 근거가 아니라
  안심의 *느낌*만 준다.
  → **후속(23:1x): 쟀다.** 실제 리스너로 네 변종 측정 — **대조군 18건 → CSP 0건**, `loadHTMLString`·
  `loadFileURL` 동일, **`data:` 래스터는 네 변종 모두에서 표시**(과차단 아님). **이제 "2겹"이 근거를 갖는다.**
  → 그리고 **낡음 방지 장치**를 같이 걸었다: 스파이크가 잰 정책 문자열과 앱이 주입하는 문자열이
  같은지 단위 테스트가 단언한다. **정책을 고치면 스파이크 결과가 낡는데, 그 사실이 어디에도
  안 걸리면 낡은 실측을 근거로 계속 쓰게 된다.**
- **안전한 매칭을 완전한 매칭으로 읽는 것** — 실측(frontend-junior, `xlink:href`):
  `<base` 를 부분 문자열로 찾다 `<basefont>` 까지 지운 사고 뒤 **이름을 경계로 찾도록 고쳤다.**
  옳은 수정이다. **그런데 그 수정이 `xlink:href` 를 숨겼다** — 경계 규칙 덕에 `href` 가
  `xlink:href` 안에서 안 걸리고(옳은 동작), **그래서 따로 이름을 대기 전까지 아예 안 보였다.**
  **부분 문자열 매칭이었다면 틀린 이유로 우연히 잡혔을 것이다.**
  → **경계를 지키는 것과 목록을 채우는 것은 별개의 일이다.** 앞의 것을 고치면 뒤의 것이
  따라온다고 착각하기 쉽다 — 오히려 **정확해진 매칭이 목록의 구멍을 더 조용하게 만든다.**
  → 관련 일반형(오늘 네 사례가 한 문장으로 모인다): **문자열 검색은 경계를 모른다.**
  `src=`↔`data-src=` · `<base`↔`<basefont>` · `pkill -f "CodeNavigator"`↔`CodeNavigatorPackageTests`
  · 그리고 `href`↔`xlink:href`. **셋은 코드에서, 하나는 셸에서 났다 — 언어 문제가 아니라 습관이다.**
- **넓은 면적의 색으로 화면 전체를 판정하는 것** — 실측(QA, 라이트 모드): 전체 창을 보고

  어느 쪽이 틀렸는지 모른다.**
- **테스트 *이름* 목록으로 커버리지를 판정하는 것** (리더 자기 정정, 22:4x) — 새니타이저
  테스트 21건의 **이름**에 `<base>`·`meta refresh` 가 없어서 **"코드는 막는데 테스트가 없다"고

  **테스트를 먼저 읽게 했더니 살아남을 쪽의 결함 셋이 나왔다**(D-12 · 프로토콜 상대 참조
  `//evil.com` 을 로컬로 읽어 허용 · 루트 자신을 리소스로 허용).
  → **구현은 중복이어도 테스트는 중복이 아니다.** 두 사람이 같은 규칙을 다르게 상상했으므로
  각자의 테스트가 상대의 사각을 덮는다. 지우기 전에 읽는 비용은 몇 분이고, 안 읽으면
  **커버리지만 줄고 구멍은 남는다.**
  → 리더 몫: 이 중복은 **내 중복 지시**와 **시니어의 스코프 초과**가 겹쳐 생겼다. 낭비가
  결과적으로 결함 셋을 샀지만 **그것이 중복을 정당화하지는 않는다.**
- **경로 해석 함수가 "항상 해석한다"고 믿는 것** — 이 빌드에서 **경로 비교가 네 번째로 물었다.**
  실측(D-12, 리더 독립 재현): `URL.resolvingSymlinksInPath()` 는 **leaf 가 존재하지 않으면
  심링크를 풀지 않는다.**
  ```
  leaf 존재  link/exists.md → outside/exists.md  차단 ✅
  leaf 없음  link/later.md  → root/link/later.md 허용 ❌  ← 미해석 경로가 접두 비교 통과
  ```
  → **주석은 "양쪽 다 해석하고 비교한다"고 정확히 적혀 있었다. 구현이 그 약속을 조건부로만
  지킨다.** 앞선 세 번(`/tmp`↔`/private/tmp` · 탭 정체성 · 접두 비교)은 *비교 방식*이 문제였는데
  이건 **해석 자체가 조용히 생략되는 경우**다.
  → **문자열 픽스처로는 영원히 안 잡힌다.** 실제 심링크를 만들어야 하고, **leaf 있는 경우와
  없는 경우를 둘 다** 넣어야 한다 — leaf 있는 케이스만 있으면 통과한다.
- **한 함수가 정체성과 보안 경계를 겸하는 것** — D-12 의 구조적 원인. `ProjectIdentity.canonical`
  이 *"두 경로가 같은 프로젝트인가"* 와 *"이 경로가 루트 안인가"* 를 동시에 답하고 있었다.
  **둘은 해석 실패 시 정반대로 행동해야 한다** — 정체성은 관대해야 하고 **보안은 차단**이어야 한다.
  → **한쪽 요구로 고치면 다른 쪽이 조용히 바뀐다.** 공유해야 할 것은 *구현*이 아니라 *계약*이다
  ("해석 후 비교 · 구분자 포함 · **해석 실패 시 보안 경계는 차단**").
  → 부수 효과: 검사한 경로가 아니라 **해석된 경로를 로드**하면 TOCTOU 창까지 닫힌다.
- **한 측정을 깎는 논증이 내 측정은 비껴간다고 믿는 것** — 나는 프론트의 spike 결과(자모 낱개)를
  **"합성 입력 아티팩트"** 로 깎았다. **QA 가 그 논증을 자기 데이터에 그대로 적용했다**:
  > 내 18바이트 측정도 `key code`(합성 CGEvent)로 쳤다. **합성 입력이 IME 조합을 건너뛴다면
  > 앱이 정상이어도 자모가 나온다.** 내 관측은 *"앱이 조합 못 함"* 과 *"합성이 조합 안 됨"* 을
  > **구분하지 못한다.**
  → **맞다.** 나는 남의 측정을 깎는 데 쓴 잣대를 **우리 편에 유리한 측정에는 안 댔다.**
  D-13 은 우리가 이미 믿는 결론이었고, **믿는 결론을 지지하는 증거는 검사를 덜 받는다.**
  → **논증은 대상을 가리지 않는다.** "합성 입력을 못 믿는다"가 참이면 **합성으로 얻은 모든 것**이
  같은 등급으로 내려간다 — 그게 우리 가설을 반박하든 지지하든.
  → **결론은 살아남았지만 근거가 바뀌었다**(QA 가 구해 냈다): `EditorGridView` 에
  `interpretKeyEvents`·`inputContext`·`NSTextInputClient` 참조가 **0건**이다. **입력 컨텍스트에
  참여하지 않는 뷰에는 조합 단계가 존재하지 않으므로, 합성이든 실제 키보드든 결과가 같다.**
  → **약한 측정 + 강한 구조 = 성립.** 측정만으로 주장했으면 틀린 근거 위에 옳은 결론을 세운
  셈이었을 것이고, 그건 다음 사람이 근거를 확인할 때 무너진다.
- **한 검사 도구를 모든 대상에 쓰는 것** — 나는 아침에 *"`strings` 로 Swift 심볼을 찾지 마라"*
  를 §6 에 넣었다. **QA 가 정확히 반대 경우를 만났다**: `currentDirectoryURL` 을 `nm` 으로 찾으면
  **0건(거짓 음성)** 이고 **`strings` 로는 잡힌다** — Foundation 프로퍼티라 심볼 테이블에 없다.
  → **교훈은 "`strings` 를 쓰지 마라"가 아니라 "도구를 대상의 종류에 맞춰라"** 였다.
  맹글된 Swift 심볼은 `nm`, Foundation API 문자열은 `strings`. **내가 규칙을 너무 좁게 적었고,
  그대로 따랐다면 QA 는 "D-16 이 번들에 없다"고 판단했을 것이다.**
  → 두 경우 모두 **양성 대조가 살렸다**(`openProject` 21건). **도구를 바꿀 때마다 양성 대조를
  다시 돌리는 것**이 어느 도구가 맞는지 아는 것보다 안전하다 — 틀린 도구는 언제나 다시 나온다.
- **`strings` 로 Swift 심볼을 찾는 것** — 실측: 번들에 수정이 들어갔는지 `strings | grep` 으로
  확인해 **"심볼 없음"이라는 거짓 음성**을 받았다. **Swift 심볼은 맹글돼 심볼 테이블에 있고
  `strings` 는 그걸 못 본다.** `nm` 으로 다시 재니 14건이었다.
  → **하마터면 들어가 있는 수정을 "안 들어갔다"고 팀에 보고할 뻔했다.** 양성 대조(`openProject`
  26건)를 같이 돌렸기에 도구 문제임이 즉시 드러났다. **검사기를 바꿨으면 양성 대조도 다시 돌려라.**
- **임계값을 직관으로 유도하는 것** — 실측(backend-senior, AC-3 메모리 검사): 새 검사를 쓰고
  통과시킨 **직후 변이를 넣었더니 그대로 초록**이었다. 픽스처가 작아 누수가 잡음에 묻혔다.
  키운 뒤에도 **두 번 더 놓쳤다** — 경계를 인덱스 크기의 1/2, 1/4 로 잡았는데 둘 다 통과.
  → 원인은 직관이었다: *"인덱스가 5MB 면 못 놓을 때 회당 5MB 늘 것"*. **실제 누수는 회당 1.0MB.**
  할당자가 페이지를 압축·공유해 **"붙들고 있는 양"과 "footprint 증가"가 1:1 이 아니다.**
  → **임계값은 유도하는 게 아니라 양쪽을 재서 고르는 것이다** — 정상(0.08MB)과 누수(1.06MB)를
  둘 다 재고 그 사이를 골랐다. **"추론으로 메우지 마라"의 수치판.**
  → 그리고 **새 검사는 나중이 아니라 쓴 직후에 깨뜨려 봐야 한다.** 오늘 우리는 남의 초록불을
  여러 번 의심했는데, **방금 자기가 만든 것도 같은 자리에 있다.**
- **결함이 자신을 관측하는 실험을 오염시키는 것** — 실측: 기동에 실패한 인스턴스는 **`quit` 이
  먹지 않았다**(pid 75939 유지). 그래서 "실패를 보고 상태를 초기화한다"는 실험 절차가
  **실패했을 때만 실패한다.** 관측자는 새 시행이라 믿고 같은 오염된 인스턴스를 계속 잰다.
  → **흡수 상태는 결과를 0 으로 못 박을 뿐 아니라 그것을 벗어나려는 시도까지 흡수한다.**
  → 상태 초기화는 **성공을 확인할 때까지 escalate** 하고(quit → kill → kill -9 → `pgrep` 0 확인),
  **초기화 성공 자체를 시행 데이터로 기록**한다. 확인 없는 초기화는 초기화가 아니다.

  숨기는 것과 붙들고 있는 것 사이에 **기록**이 있다.
