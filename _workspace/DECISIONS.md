2. **정규화·정체성은 엔진.** 앱이 두 번째 방법으로 같은 질문에 답하지 않는다.
3. **요구를 더 잘 만족하는 쪽이 이긴다** — 저자가 누구인지가 아니라. (렌더 정책 때 시니어가

   두 사람이 같은 규칙을 다르게 상상했으니 각자의 테스트가 상대의 사각을 덮는다.
   **⚠ 오늘 넷 다 버린 쪽에서 뭔가를 건졌다**: 렌더 병합에서 **결함 셋**(D-12 · `//evil.com` ·
   루트 자신), 탭 복원에서 **테스트 셋**(활성 탭이 *사라진* 경우 · 전부 실패와 첫 실행의 구별 ·
   `복원 + 빠짐 = 저장 수` 불변식).
   → **그래서 이건 중복 해소 절차가 아니라 은퇴 절차다**: 어떤 코드를 은퇴시킬 때
   **구현만 지우고 테스트는 읽는다.** 중복이 아니어도 마찬가지다 — 죽은 모듈의 테스트가
   살아 있는 모듈의 사각을 덮고 있을 수 있다(오늘 `ProjectIdentity` 대소문자 케이스가 그랬다).

**⚠ 왜 반복되나 — 구조적 원인:**
**새 개념이 앱과 엔진 양쪽에서 동시에 필요할 때, 착수 전에 소유자가 정해지지 않는다.**
각자 자기 쪽에서 합리적으로 만들고, 며칠 뒤 둘이 만난다.

**→ 규칙: 앱·엔진 양쪽에 걸치는 새 개념은 착수 전에 리더에게 소유자를 물어라.**
*"내 쪽에서 이걸 만들어야 하는데 엔진에도 있을 법한가?"* 를 묻는 데 드는 비용은 1분이고,
중복의 비용은 **두 사람 몫의 구현 + 어느 쪽을 버릴지 정하는 판단 + 테스트 이관**이다.

스위트 하나가 아니라 **넷**이었다.

**⚠ 그리고 두 번째를 잡아낸 보고 자체가 또 오산했다** — "스위트 둘 · 테스트 8건"으로 왔지만
실제는 **스위트 넷 · 테스트 20건(미이관 10건)**이었다. 즉 *조심하려고 다시 읽은 사람도* 틀렸다.

→ **결론: 이건 주의력 문제가 아니다.** "더 꼼꼼히 읽어라"는 이미 실패한 처방이다.
**세는 일을 눈에서 명령으로 옮긴다.**

```bash
# 파일이 실제로 무엇을 담고 있나 — 지우기 전에 반드시 이걸로 센다
grep -nE '^@Suite|^\s*@Test' <파일>          # 스위트·테스트 전수
grep -cE '^\s*@Test' <파일>                  # 건수
```

**은퇴 보고는 산문이 아니라 표다.** 위 명령의 출력 전건이 행이 되고, 각 행에 목적지가 있어야
한다. 목적지는 **실재하는 `파일:라인`** 이어야 한다 — "이관했다"는 주장이 아니라 가리킴이다.

| # | 테스트 이름 | 판정 | 목적지 |
|---|------------|------|--------|
| 1 | … | 이관 / 이동 / 폐기 | `Tests/…Tests.swift:88` (폐기면 *왜 안 재도 되는지*) |

행 수가 `grep -c` 와 다르면 그 보고는 반려한다. **표의 길이가 명령의 출력과 같다는 것이
"전부 봤다"의 유일한 증거다.**

## ✅ D-19 닫힘 — 축은 모드가 아니라 화음이었다

내 진단서는 *"base 가 ASCII 가 아니면 물리 키로 되돌려라"* 였다. **시니어의 축이 더 정확했다:**

> **화음은 산문이 아니다. 한글은 ⌃ 를 누르지 않고 친다.**

내 규칙은 **결과**(비ASCII)를 보고 판단하고, 채택된 규칙은 **의도**(화음이냐 산문이냐)를 본다.
비ASCII 산문은 번역하면 안 되는데 내 규칙으론 그게 안 갈린다.

```swift
if stroke.modifiers.contains(.control) || stroke.modifiers.contains(.command) { return true }
return editorMode != .insert
```

**⌥ 를 뺀 것이 이 수정의 핵심 판단이다** — macOS 에서 ⌥ 는 *글자를 만드는* 수식어다(`⌥e` → `é`).
묶었으면 조합 입력이 전부 죽어 **원래 결함보다 나쁜 수정**이 됐다.

> **"수식어가 있으면 명령"이 아니라 "글자를 안 만드는 수식어면 명령"이다.**

### 일반형으로 쓴 값이 여기서 나왔다
수정 전 **두벌식 `⌃A`~`⌃Z` 26칸 전부 Red.** `⌃C` 하나로 테스트를 썼으면 그 칸만 고치고 끝났다.
QA 가 밟은 건 26칸 중 3번째였을 뿐이다.

### ⚠ `⌃[` 의 생존이 하루에 두 번 우리를 속였다
두벌식이 **기호 키를 안 바꾼다**는 우연 하나 때문에 `⌃[` 는 계속 옳게 동작했다. 그 결과:
- 아침: `isInsertModeExit` 진단에서 *"`⌃[` 는 되니까 탐지는 멀쩡"* 으로 읽혔다
- 저녁: 범위 판정에서 *"`⌃C` 만 문제"* 로 읽혔다 (실제로는 26칸)

**→ 규칙: 우연히 옳은 결과는 "여긴 멀쩡하다"의 근거가 될 수 없다.**
왜 옳은지 설명할 수 없으면, 옳은 것도 증거가 아니다.

### 수정의 위험이 결함의 위험보다 컸다
화음을 살리려다 전부 번역하면 `ㄱ` 이 `r` 로 나간다 — **결함보다 나쁜 수정.**
그래서 반대 방향 방어선을 세우고 **변이로 실측**했다(`return true` → 그 테스트만 빨강).
→ **수정이 결함보다 위험할 수 있는 자리에서는, 고친 방향뿐 아니라 망가뜨릴 방향에도 방어선을 세운다.**

2. 검사가 **형제를 탭으로 안 열었다** → 잘못 고른 결과로 무엇을 잃는지 볼 대상이 없었다

**진짜 피해는 라우팅이 첫 일치에서 멈춘다는 것**이다. 형제가 먼저 걸리면 그 세션이 거절하고
루프가 끝나 **맞는 탭은 영영 못 받는다 — 저장이 조용히 버려진다.**

→ **제품의 두 번째 방어선이 검사의 판별력을 죽인다.** 결과가 옳게 나오므로 검사는 만족하는데,
그 옳음은 잰 층이 아니라 **아래층이 만든 것**이다.
→ **규칙: 층 하나를 검사할 때는 아래층 방어를 끄거나, 아래층이 못 가리는 피해를 대상으로 삼는다.**

## 종료 경로 — 계약 경계 (D-20 이 처음 밟는다)

```
✅ 엔진:  shutDown() 이 죽은 것을 확인하고 돌아온다 (SIGTERM → 0.1초 → SIGKILL, isRunning 폴링)
🔴 앱:    종료 전에 그것을 기다리는 코드가 없다
```
`NSApplication.terminate:` 는 비동기 정리를 안 기다린다 → `applicationShouldTerminate` 에서
`.terminateLater` 로 붙잡고 `shutDown()` 후 `reply(toApplicationShouldTerminate:)`.

**nvim 은 stdin EOF 를 받아도 `/dev/null` 로 다시 열고 산다** — 그래서 SIGKILL 까지 필요하다.
리더 실측: 고아 2개가 `kill` 에 안 죽고 `kill -9` 로만 죽었다.
**실측 수치**: 정상 종료 2회 = 고아 0 · **비정상 종료 = 고아 10.**

⚠ 세션 정리는 백엔드 소유, 종료 훅은 프론트 소유. **`shutDown()` 변경은 백엔드에 요청한다.**

풀게이트를 돌렸는데 **같은 실행 안에서 트리가 바뀌었다:**

```
AC-3 메모리 스텝   🔴 FAIL   ← 그 사이 새 파일이 들어와 컴파일이 깨졌다
```
**이 결과는 어느 한 시점의 상태도 말하지 않는다.** 근거로 쓰지 않는다.

**그리고 내 격리 확인이 허술했다** — `swift-test|swiftpm-testing-helper` 만 셌고 **`swift build` 는
안 셌다.** 실제로는 SwiftPM 다른 인스턴스가 `.build` 를 잡고 있었다(내 명령이 그것을 기다렸다).
**체커의 사각 — 오늘 세 번째다**(`pgrep -c` 부재 · `--include` 글로브 · 이것).

→ **인증용 풀게이트는 조용한 창에서만 유효하다.** 팀이 편집 중일 때 돌린 게이트는
"지금 초록/빨강"이 아니라 **"돌리는 동안의 어딘가"** 를 잰다.
→ **격리 점검은 테스트 프로세스가 아니라 `.build` 를 잡는 모든 프로세스를 센다.**

## 🔴 리더 정정 — "앱에 종료 대기 코드가 없다"는 틀렸다

내가 프론트 주니어에게 보낸 표에 `🔴 앱 쪽: 종료 전에 shutDown() 을 기다리는 코드가 없다` 라고
적었다. **사실이 아니다.** 주니어가 정정했고 내가 코드로 확인했다:

```swift
// CodeNavigatorApplication.swift:190   이미 있다. 내가 요구한 형태 그대로.
func applicationShouldTerminate(_) -> NSApplication.TerminateReply {
    Task { await engine.shutDown(); await MainActor.run { NSApp.reply(...) } }
    return .terminateLater
}
// NeovimChannel:82-100   SIGTERM → isRunning 폴링 → SIGKILL → waitUntilExit
```
주석에 실측까지 적혀 있다 — *"고아는 몇 시간 살아남고 SIGTERM 을 무시한다"*.

**어떻게 틀렸나**: 백엔드가 *"엔진 쪽은 고쳐 뒀다. 앱이 종료 전에 `shutDown()` 을 기다리기만
하면 된다"* 고 했고, 나는 그것을 **앱에 그 코드가 없다는 뜻으로 읽어 그대로 중계**했다.
**엔진 소유자가 앱 영역에 대해 한 말을, 내가 앱을 안 보고 발견으로 옮겼다.**

→ **내가 오늘 팀에 세 번 요구한 규칙을 내가 어겼다**: *"타 영역의 주장은 중계 전에 1회 실측하거나
'○○ 통지 기준'임을 명시한다."* 실측은 30초였고 나는 안 했다.

**남는 경고는 유효하다**: 코드는 있지만 **그 경로가 한 번도 실행된 적이 없다.** 빠진 것은
구현이 아니라 **라이브 확인 하나**다. 그 구분을 흐린 게 내 잘못이고, 주니어가 측정 시각을
붙여 돌려준 방식이 옳다.

## ⚠ 변이 실측 중에는 번들을 자르지 못한다 — 창을 서로 알려야 한다

내 `bundle.sh` 가 두 번 실패했다:
```
error: input file 'MenuSystemAction.swift' was modified during the build
```
그 순간 주니어는 **양성 대조 중**이었다 — 창 동작을 앱 동작으로 잘못 분류해 넣고
테스트가 발화하는지 본 뒤 되돌리는 중. **일부러 망가뜨린 상태였다.**

**이 트리에는 방어선 실측 때문에 깨진 코드가 상시로 있다.** 커밋에 대해서는 이미 규칙이 있다
(변이 표지 검사 후 파일 명시). **번들·게이트에는 없었다.**

→ **규칙: 변이 실측에 들어가기 전에 한 줄 알린다. 끝나면 한 줄 알린다.**
   그 창 안에서 잘린 번들·돌린 게이트는 **일부러 망가뜨린 순간의 스냅샷**이라 근거가 못 된다.
   (주니어가 먼저 제안했다.)

**⚠ 그리고 이것이 "게이트는 원자적이지 않다"의 두 번째 얼굴이다** — 앞의 것은 *팀이 정상 작업을
하는 중*이었고, 이번은 *팀이 일부러 깨뜨린 중*이었다. 후자가 더 나쁘다: 결과가 그럴듯하게
빨간불이라 **진짜 회귀로 오독하기 쉽다.**
